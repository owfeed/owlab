# Диагностика

[English](troubleshooting.md)

Эта страница ведёт от ошибки или симптома owlab к причине и решению. Она для тех, у кого лаборатория
не собирается, не стартует или ведёт себя не так, как описано в `owlab.yaml`.

- Всё здесь наблюдалось на работающем роутере.
- Каждая запись — симптом или точное сообщение, затем причина, затем решение.
- **Решение** говорит, что owlab теперь с этим делает. Если действовать нужно вам, решение говорит, что
  запустить.
- Записи сгруппированы по тому, как проблема выглядит: почти ничто здесь не похоже на свою причину.
- Ищите на странице точный текст, который видите. Сообщения приведены дословно.

## Сборка образа падает

### Индекс в образе старше слоя, который им пользуется

**Симптом.** `owlab up` падает на установке файла из `extra_packages:` на роутере 24.10. Он называет
пакет, который никто не просил:

```
opkg_install_pkg: Checksum or size mismatch for package bash. Either the opkg
or the package index are corrupt. Try 'opkg update'.
owlab: build failed: exit status 1
```

- `bash` здесь — **зависимость** установленного пакета, а не он сам.
- Происходит только на линии opkg.

**Причина.** `opkg update` выполнялся в более раннем слое, чем установка. Индекс в образе бывает на
месяцы старше установки, которая его читает.

**Решение.** `opkg update` выполняется в том же слое, что и установка. `owlab test` обновляет индекс и
перед установкой локального файла.

<details>
<summary>Почему индекс устаревает и почему apk это не касается</summary>

Buildkit держит слой с `opkg update` ровно столько, сколько не меняются релиз и список пакетов из
фида. Слой установки перезапускается при любом изменении подготовленных файлов.

Пин на точечный релиз не спасает: релиз не заморожен. OpenWrt пересобирает пакеты внутри
`releases/24.10.8/` на месте, не меняя версию. Замерено 2026-09-04 против образа, собранного
2026-07-29:

```
индекс в образе        bash 5.2.37-r1  Size 473650  SHA256 f1872e60...
downloads.openwrt.org  bash 5.2.37-r1  Size 473647  SHA256 20eaa220...
```

Одна и та же версия, разные байты. Ровно это opkg и называет несовпадением контрольной суммы.

apk не нужно ни то, ни другое. apk-tools 3.0.5 сам перепроверяет кэшированный индекс старше
`--cache-max-age` (по умолчанию 4 часа). Поэтому `apk add` в месячном образе перекачивает все APKINDEX
прежде, чем что-либо разрешать. У opkg такой политики нет: он читает то, что оставил последний
`opkg update`, и ничего не спрашивает.

</details>

### `extra_packages` одного роутера отменили сборку всех остальных

**Симптом.** `owlab up` падает на шаге extras одного роутера. Вместе с ним останавливаются роутеры,
которые собирались нормально:

```
#33 ERROR: process "/bin/sh -c set -eu; ... opkg install --force-overwrite ..." exit code: 255
#18 [imm2410 stage-3  2/12] ...   #18 CANCELED
#24 [imm2512 stage-3  2/12] ...   #24 CANCELED
owlab: build failed: exit status 1
```

**Причина.** `docker compose build` кладёт все роутеры в один solve buildkit. Buildkit отменяет весь
solve на первой упавшей цели. Шаг extras выходил с ненулевым кодом из-за одного подготовленного файла,
и один пакет на одном роутере стоил всей лаборатории.

**Решение.** Шаг extras ставит весь набор разом. Если это не вышло, он ставит каждый файл по
отдельности, чтобы исправные всё-таки встали. Файл, который так и не встал:

- назван в логе сборки;
- записан в `/etc/owlab/extras-failed`;
- сообщён `owlab up` после его таблицы;
- роняет `owlab test`.

`owlab up` сообщает об этом так:

```
! owrt2410 is running WITHOUT luci-app-example_1.0_all.ipk
!   Every other router built and started; only these packages are missing.
!   The package manager said why during the build — one router at a time shows it again:
!     owlab up --rebuild owrt2410
```

Напечатав это, `owlab up` завершается с ненулевым кодом. Лаборатория поднята, и остальные роутеры
пригодны. Но это не то, что описано в конфиге. Скрипт, который запускает `owlab up` перед своими
проверками, не должен принимать одно за другое.

**Проверка.** Спросите работающий роутер напрямую:

```console
$ owlab exec owrt2410 -- cat /etc/owlab/extras-failed
luci-app-example_1.0_all.ipk
```

<details>
<summary>Почему настройкой сборки это не лечится</summary>

Так ведут себя обе линии релизов: дело в `set -eu`, менеджер пакетов ни при чём. Замерено 2026-09-04:
opkg выходит с 255 на неразрешимой зависимости, apk — с 27 на `unable to select packages`. Оба раза
соседние роутеры в том же запуске получили CANCELED.

Запасной настройки на стороне сборки нет. Ни у `docker compose build`, ни у `docker buildx bake` нет
`--keep-going`.

</details>

### Один недоступный фид ронял сборку до того, как ставился хоть один пакет

**Симптом.** `owlab up` падает в stage-3, ещё не установив ни одного пакета. Последнее, что видно в
логе, — сообщение самого менеджера о том, что с остальными фидами всё в порядке:

```
ERROR: wget: exited with error 8
WARNING: .../kmods/6.18.33-1-<hash>/packages.adb: unexpected end of file
1 unavailable, 0 stale; 10206 distinct packages available
owlab: build failed: exit status 1
```

Это происходит на каждом запуске против такого образа, а не время от времени.

**Причина.** Образ запрашивает каталог kmods, которого фид больше не отдаёт, и получает 404 на этот
один подындекс. Оба менеджера завершаются с ненулевым кодом из-за одного недоступного фида. Шаг
выполнялся под голым `set -eu`, поэтому такой код обрывал слой до цикла установки пакетов.

**Решение.** Обновление индекса продолжается, если прочитан хотя бы один фид. Если не прочитан ни
один, сборка по-прежнему падает. owlab выводит заново весь вывод менеджера, поэтому фид, который не
ответил, назван. Следом идёт строка о том, с чем установка продолжается:

```
owlab: apk update: partial refresh, 8 feed(s) read, 11279 packages available; ...
```

**Проверка.** Спросите роутер, что делает его обновление, и посчитайте открытые фиды:

```console
$ owlab exec owrt2512 -- 'apk update 2>&1 | grep -c "^ \["'    # прочитано фидов; 0 — ни одного
$ owlab exec owrt2410 -- 'opkg update 2>&1 | grep -c "^Updated"'
```

| Число | Код возврата | Значение |
|---|---|---|
| 0 | любой | фатальный случай; owlab об этом скажет |
| больше нуля | ненулевой | частичный случай |

Имя, которое установка после частичного обновления не нашла, считается сбоем: его мог нести не
ответивший фид; см. [следующий раздел](#owlab-up-выходит-с-кодом-1-роутер-работает-без-пакета-из-packages).
Если не ответил только индекс kmods, сбоем считается только ненайденный `kmod-*`.

<details>
<summary>Почему индекс kmods пропадает и почему число пакетов — не проверка</summary>

Индекс kmods назван по хешу ядра, с которым собран образ (`kmods/6.18.33-1-<hash>/packages.adb`). Фид
хранит лишь последние несколько сборок ядра. Образ старше этого окна будет получать 404, пока не
пересоберут сам образ. Ретрай тут не инструмент: это 404, а не залипание.

Измерено: `apk update` выходит с кодом 1 при одном битом фиде из девяти на 25.12.4. `opkg update`
выходит с кодом 1 при одном из восьми на 24.10.8. Цикл, который обрывал этот код, уже написан терпимым к пакету, которого в
этом фиде нет.

Количество пакетов в итоговой строке apk намеренно не считается всей проверкой. Если увести все фиды на
несуществующий хост, apk всё равно напишет `8 unavailable, 0 stale; 136 distinct packages available` и
завершится с кодом 8. Эти 136 берутся из базы установленных пакетов, а не из фида. Различает эти два
случая только число прочитанных фидов.

</details>

### `owlab up` выходит с кодом 1: роутер работает БЕЗ пакета из `packages:`

**Симптом.** `owlab up` печатает свою таблицу, потом это, и выходит с кодом 1:

```
! owrt2410 is running WITHOUT luci-app-example
!   Every other router built and started; only these packages are missing.
!   The package manager said why during the build — one router at a time shows it again,
!   and downloads what failed to download:
!     owlab up --rebuild owrt2410
!   A package the rebuild refuses again cannot go on that router: take it out of the
!   router's packages: (a "-name" entry for one owlab installs by default) or extra_packages:.
```

В 0.6.6 и раньше тот же роутер стартовал с кодом 0. Единственным следом была строка
`owlab: FAILED to install` в логе сборки.

**Причина.** Слой пакетов ставит набор одним вызовом. Если это не прошло, он ставит каждое имя отдельно
и записывает те, что не встали, в `/etc/owlab/packages-failed`. Причину лог сборки называет над строкой
`owlab: FAILED to install <name>`:

| Причина в логе сборки | Значение |
|---|---|
| `owlab: <name> did not download in 4 attempts` | Сбой сервера загрузок или сети. Пакеты после него запрашиваются по одному разу, так что один сбой стоит одного круга ожидания. |
| Строки самого менеджера пакетов | Конфликт файлов или зависимость, которой нет в фидах. |
| `no feed that answered the refresh above carries it` | Имя не нашлось после `partial refresh`, а не ответивший фид мог его нести. |

**Решение.**

- После сбоя сети запустите `owlab up --rebuild owrt2410`. Обычный `owlab up` берёт слой из кеша и
  снова сообщает о том же роутере.
- При конфликте или недостающей зависимости уберите имя из `packages:` этого роутера или добавьте
  пакет, который ему нужен. Для пакета, который owlab ставит по умолчанию, убрать — значит добавить
  запись `-имя`.

**Проверка.** Спросите работающий роутер:

```console
$ owlab exec owrt2410 -- cat /etc/owlab/packages-failed
luci-app-example
```

`owlab test` проваливает этот роутер на шаге `packages` с теми же именами.

## Роутер вообще не отвечает на опубликованном порту

### Интерфейс контейнера не попал ни в одну зону firewall

**Симптом.** `owlab up` пишет `did not answer on HTTP in time` и выходит с кодом 1.

- `curl` на опубликованный порт не получает ничего: код выхода 52, пустой ответ.
- Внутри контейнера `uhttpd` слушает `0.0.0.0:80`, и локальный запрос отрабатывает.
- Замечено на ImmortalWrt. Два роутера были недоступны, а роутеры OpenWrt на том же стенде работали.

```console
# uclient-fetch -O- http://127.0.0.1/cgi-bin/luci/
HTTP error 403                                              <- LuCI просит логин: так и надо
$ curl -o /dev/null -w '%{http_code}\n' http://localhost:18026/cgi-bin/luci/
000
```

То, что `owlab logs` обрывается на `- generating board file -`, ни о чём не говорит. Это последняя
строка, которую печатает здоровый контейнер.

**Причина.** Зона lan не разрешилась ни в одно устройство, и fw4 не дал строки jump в неё. Пакет доходит
до конца цепочки input и попадает в `jump handle_reject`, то есть получает TCP reset.

- С хоста это выглядит как пустой ответ.
- Из соседнего контейнера той же docker-сети — как `Connection refused`.

```console
# nft list ruleset | sed -n '/^\tchain input {/,/^\t}/p'
chain input {
        type filter hook input priority filter; policy drop;
        iifname "dummy0" jump input_wan     # ... и ни одной строки про br-lan
        jump handle_reject                  # значит, трафик lan приходит сюда
}
```

**Решение.** `95_owlab-base` называет lan-устройство в этой зоне явно:

- `list device 'br-lan'` рядом с уже имеющимся `network 'lan'`;
- `input ACCEPT` на ней;
- если в образе зоны для сети lan нет, она создаётся.

Firewall при этом остаётся включённым. fw4 в контейнере работает, а его отключение спрятало бы целый
класс настоящего поведения.

**Проверка.** На роутере:

```console
# nft list ruleset | grep 'jump input_lan'
        iifname "br-lan" jump input_lan comment "!fw4: Handle lan IPv4/IPv6 input traffic"
```

<details>
<summary>Как fw4 строит переход в зону</summary>

fw4 разворачивает зону в `iifname "<dev>" jump input_<zone>`. Сам `<dev>` он берёт из списка `network`
зоны в момент сборки набора правил. Зона, которая не разрешилась ни в одно устройство, не даёт строки
jump вообще.

`device` fw4 берёт буквально, не спрашивая netifd. Поэтому jump на месте независимо от того, что
netifd успел сделать к моменту чтения конфига. С сетью устройство дедуплицируется: одна строка jump,
измерено.

</details>

### ssh закрывается сразу после открытия

**Симптом.** `ssh -p 12226 root@localhost` на роутер ImmortalWrt закрывается мгновенно. HTTP того же
контейнера при этом отвечает.

**Причина.** ImmortalWrt везёт в `/etc/config/dropbear` `option Interface 'lan'`, а OpenWrt такого
ключа не везёт. Поэтому dropbear слушает один адрес вместо wildcard. Измерено на одном стенде,
`netstat -ltnp` внутри каждого контейнера:

```console
imm2512    tcp 0 0 192.168.163.5:22  LISTEN  2262/dropbear
owrt2512   tcp 0 0 0.0.0.0:22        LISTEN   889/dropbear
```

Этот адрес верен, только пока выполнены два условия: netifd успевает поднять `lan` раньше старта
dropbear, и ничего не приходит по другому адресу. Контейнер, который пересоздают так часто, ни того ни
другого не обещает.

**Решение.** `95_owlab-base` удаляет ключ, и dropbear слушает `0.0.0.0:22` на обоих дистрибутивах.

**Проверка.** `netstat -ltn` внутри контейнера должен показать `0.0.0.0:22`.

## Роутер отдаёт LuCI, но ничего не работает

### procd джейлит сервисы, а контейнер не может построить джейл

**Симптом.** Роутер без DNS-сервера.

- `service dnsmasq status` говорит `not running`, а запуск внешне проходит успешно.
- Любой пакет, который настраивает dnsmasq форвардить на вспомогательный демон, настраивает демона,
  которого нет.

**Причина.** procd джейлит изрядное число сервисов. Джейлу нужны неймспейсы, создавать которые
контейнеру не разрешено:

```console
$ ujail -n test -p -- /bin/true
jail: failed to clone/fork: Operation not permitted
```

procd считает это падением и респавнит. Сервис сидит в вечном crash loop, единственный след которого:

```
procd: Instance dnsmasq::cfg01411c s in a crash loop 6 crashes
```

Тот же бинарь, запущенный руками с тем же сгенерированным конфигом, работает прекрасно. Из-за этого
причину и тяжело найти.

**Решение.** owlab убирает `/sbin/ujail` из образа контейнера. Без него procd запускает сервис
напрямую, поэтому это именно решение, а не обход. Роутер `fidelity: vm` работает на своём ядре и
джейлы сохраняет.

<details>
<summary>Почему не выдать контейнеру нужную capability</summary>

Альтернатива — выдать контейнеру `CAP_SYS_ADMIN`. Это слишком близко к руту на хосте, чтобы
одноразовая коробка имела право такое просить.

Теряется граница безопасности между сервисами внутри контейнера, который и так одна зона доверия.

Так было во всех контейнерах owlab с самого начала. Не замечали, потому что LuCI рисует страницы DHCP и
DNS из конфига, а не из живого демона.

</details>

### Роутер сбрасывает каждое соединение

**Симптом.** TCP подключается и тут же получает reset («connection reset by peer»). `uhttpd` при этом
жив и слушает `0.0.0.0:80`. Только на ImmortalWrt.

**Причина.** ImmortalWrt включает `flow_offloading` по умолчанию. Правилу нужен флоутейбл, а
флоутейблу — `nf_flow_table` в работающем ядре. Где его нет, nft отвергает **весь** ruleset. Базовые
цепочки остаются с `policy drop` и без единого перехода в зоны.

**Решение.** `95_owlab-base` создаёт флоутейбл в скрэтч-таблице и удаляет его. Настройку он выключает,
только если это не удалось.

Сначала идёт `modprobe`. OpenWrt не поставляет `modules.alias`, поэтому ядро не может автозагрузить
модуль по алиасу, который просит nft. Без `modprobe` проба врала на вполне способном роутере.

### LuCI отвечает, но исходящее не работает

**Симптом.** LuCI отдаёт 200, а любое исходящее соединение висит без ошибки. `apk` выглядит зависшим.

**Причина.** mwan3 решает, что фиктивный WAN мёртв, и ставит
`2061: from all fwmark 0x3d00/0x3f00 blackhole`.

**Решение.** `95_owlab-base` останавливает и отключает mwan3 и watchcat. Firewall в этот список
намеренно не входит: fw4 работает, а его отключение спрятало бы целый класс настоящего поведения.

## Пакет установился и ничего не делает

### Установка с `--feed` останавливается: «the feed under test ... was not read»

**Симптом.** `owlab test --feed` или `owlab install --feed` падает на шаге установки:

```
owlab: the feed under test (owlab-feed: https://.../packages.adb) was not read: ...
Refusing to install by name, because apk would take a same-named package from another feed instead.
```

Выше напечатана причина от самого менеджера:

| Причина выше | Проблема |
|---|---|
| `unexpected end of file` или `Failed to download` | 404 |
| `UNTRUSTED signature` или `Signature check failed` | чужой ключ |

**Причина.** Роутер не смог прочитать тестируемый фид. URL неверный или отдаёт 404, либо индекс
подписан не тем ключом, что передан в `--feed-key`.

**Решение.** Исправьте URL или ключ и запустите снова:

- apk нужен URL самого `packages.adb`; opkg — каталог, где лежит `Packages.gz`.
- Для opkg файл ключа должен называться его id (`usign -F -p <key>`).

Не ответивший дистрибутивный фид по-прежнему только предупреждение. Проверка касается одного
тестируемого фида.

**Проверка.** Спросите роутер про этот один фид. Вывода общего обновления мало: оба его очевидных
сигнала, по замерам, врут.

```console
$ owlab exec owrt2512 -- 'apk update --repositories-file /dev/null -X "$(cat /etc/apk/repositories.d/owlab-feed.list)"; echo rc=$?'
$ owlab exec owrt2410 -- 'rm -f /var/opkg-lists/owlab-feed; opkg update >/dev/null 2>&1; ls -l /var/opkg-lists/owlab-feed'
```

| менеджер | что выглядит как успех, но это не успех (измерено) | что читает owlab |
|---|---|---|
| apk 3.0.5 | ` [url]` печатается из кэша, когда индекс отдаёт 404 на повторном запуске (`0 unavailable, 1 stale`) | код возврата обновления только этого фида: 0 — прочитан; 1 — 404, чужой ключ, устаревший кэш |
| opkg (24.10.8) | индекс с плохой подписью печатает `Updated list of available packages in /var/opkg-lists/<name>`, затем `Signature check failed`, удаляет список и выходит с 0; при 404 остаётся старый список | `/var/opkg-lists/<name>`: удаляется до обновления и должен появиться после |

Из какого фида пришёл установленный пакет:

```console
$ owlab exec owrt2512 -- apk query --fields name,version,repositories tree   # URL фида рядом с lib/apk/db/installed
$ owlab exec owrt2410 -- opkg list-installed tree                             # opkg фид не записывает; сравните версию с Packages фида
```

<details>
<summary>Что было до этой проверки и повторная строка `src/gz`</summary>

До этой проверки запуск шёл дальше и проходил. Обновление считает один мёртвый фид обычным делом. После
этого `apk add <name>` / `opkg install <name>` брали одноимённый пакет из дистрибутивного фида.
Измерено на 25.12.4 и 24.10.8 с пробным фидом, отдающим 404: оба поставили дистрибутивный `tree-2.2.1`
и завершились с кодом 0.

Повторный `owlab install --feed` на том же роутере теперь заменяет прежнюю строку `src/gz owlab-feed`.
Раньше opkg брал первую строку с этим именем и пропускал остальные
(`Duplicate src declaration ... Skipping.`), так что исправленный URL не читался.

</details>

### `br-lan` не существовало

**Симптом.** Пакет ставится, запускается, рапортует об успехе и не пропускает трафик. Его правила nft
на месте, но не совпадают ни с чем.

**Причина.** `source_network_interfaces` по умолчанию `br-lan`, а lan контейнера был голым `eth0`. То
же верно для множества сниппетов firewall и hotplug-скриптов.

**Решение.** lan контейнера — мост `br-lan` с `eth0` в портах. См.
[внутренности](internals_ru.md#br-lan).

### Пакеты не из фида ставились в неверном порядке

**Симптом.** `ERROR: unable to select packages` на наборе пакетов, которые все присутствуют.

**Причина.** Они складывались под собственными именами и ставились по глобу, то есть по алфавиту.
`luci-app-example` сортируется раньше `example-daemon`, от которого зависит.

**Решение.** Они складываются с номером и отдаются менеджеру одним набором, чтобы он разрешал
зависимости между ними сам.

### Конфликт файлов молча пропустил пакет

**Симптом.** `owlab up` печатает зелёный список; пакета нет. Только на OpenWrt 24.10.

**Причина.** Пакет, зависящий от `dnsmasq-full`, тянет его за собой. `dnsmasq-full` ставит
`/etc/init.d/dnsmasq` и сталкивается с `dnsmasq`. ImmortalWrt везёт `dnsmasq-full` из коробки, поэтому
три роутера из четырёх не пострадали. Один и тот же конфиг давал на одном из них другой роутер.

**Решение.** `--force-overwrite`. Пакет из `extra_packages`, который не встал, теперь называется, а не
проходит незамеченным. Где именно, см.
[`extra_packages` одного роутера отменили сборку всех остальных](#extra_packages-одного-роутера-отменили-сборку-всех-остальных).

## DNS сломан, а сеть цела

### Движок не пропускает исходящий UDP на порт 53

**Симптом.** Демон со своим DNS-резолвером падает с
`initial rule-set: ... lookup github.com: context deadline exceeded`. На том же роутере
`https://github.com` отвечает 200. Переключение на DoH не помогает: `lookup dns.google` падает так же.

**Причина.** Часть движков (OrbStack, замерено) не форвардит исходящий UDP/53 вообще. Простой контейнер
`alpine` там ведёт себя точно так же, значит, дело в движке, а не в OpenWrt. DoH падает тоже: такой
демон сначала резолвит хост DoH через обычный UDP-сервер на 53 порту и только потом может использовать
DoH.

**Решение.** В owlab не чинится. `owlab doctor` это проверяет и называет собственный резолвер движка,
который отвечает. Пакету со своим резолвером надо бутстрапиться через него, а DoH или DoT поднимать
поверх TCP.

### Резолвер движка умирает посреди загрузки

**Причина.** Docker Desktop и WSL2 выдают `127.0.0.11`. Он реализован NAT-правилами, которые загрузка
самого OpenWrt сбрасывает.

**Решение.** `/etc/resolv.conf` держит резолвер движка первым и дописывает публичные за ним, с
`options timeout:1`.

- Полная перезапись ломает OrbStack, где публичные резолверы недостижимы.
- Отсутствие дописывания ломает Docker Desktop.
- Чтение файла перед перезаписью — то, что позволяет одному образу работать на обоих.

## Wireless не поднимается

### Всё, поставленное после загрузки, требует загрузки

**Симптом.** Радио существуют как настоящие phy и принимают команды `iw`, но
`ubus call network.wireless status` вечно показывает `up: false, pending: true`. `wifi up` отвечает
`Command failed: Not found`. Ни одна ошибка не называет причину.

**Причина.** Пакеты ставились на уже загруженную систему. Это ломает три отдельные вещи:

- **procd** не запустил `wpad`, потому что на момент загрузки сервиса не было.
- **netifd** не загрузил поддержку wireless, потому что `/lib/netifd/wireless/*` читается при старте.
- **ubusd** не получил ACL от wpad, потому что `/usr/share/acl.d/` читается при старте. Без него
  hostapd, работающий под непривилегированным пользователем `network`, не может опубликовать свой
  ubus-объект. Скрипт настройки ждёт объект, который никогда не появится.

Последнее самое неочевидное. hostapd, запущенный **под root**, регистрируется нормально, и это выглядит
как проблема прав на сокет. Сокет world-writable; воротами служат ACL ubusd.

**Решение.** Одна перезагрузка в конце провижининга VM, до применения оверлея.

### Детекция ставит каждое симулированное радио на 6 ГГц

**Симптом.** `iwinfo` показывает `Channel: 0 (unknown GHz)` и `HT Mode: null`.

**Причина.** `wifi config` выбирает самый высокий диапазон, который заявляет phy, а симулированный phy
заявляет все. При регуляторном домене `00` по умолчанию 6 ГГц не разрешает почти ничего.

**Решение.** Фикстура `wifi` назначает первому радио 2.4 ГГц, второму 5 ГГц и выставляет страну.

## У меня работает

### `--platform` всегда должен быть явным

**Симптом.** Обычный pull на arm64-хосте падает с `no matching manifest`.

**Причина.** Только `x86_64` нормализуется в настоящую OCI-платформу (`amd64`). Все остальные таргеты
публикуют нестандартную строку архитектуры (`aarch64_generic`, `mips_24kc`).

У ImmortalWrt хуже: **каждый** тег в `immortalwrt/rootfs` помечен `linux/amd64`, включая те, чьё
содержимое aarch64. Их метаданными выбрать образ нельзя вообще.

**Решение.** owlab сам распаковывает тарбол ImmortalWrt и ставит честные метаданные.

### busybox `ip` игнорирует `peer name`

**Симптом.** Контейнер в цикле перезапуска, в логе только `SIOCGIFFLAGS: No such device`.

**Причина.** `ip link add eth1 type veth peer name eth1p` создаёт пару и называет пир `vethN`. Поднятие
`eth1p` после этого падает, а `set -e` уносит с собой всю загрузку.

**Решение.** Имя пира вычитывается обратно из `ip -o link show`. Вся косметика в entrypoint работает с
выключенным errexit.

### Правка `images/` ничего не меняет, пока не пересобран бинарь

**Симптом.** Фикс «не работал», потому что в образ он не попадал. Это уже не раз давало ложный след.

**Причина.** Контекст сборки вшит через `go:embed`. Работающий бинарь несёт собственную копию.

**Решение.** После правки `images/` пересоберите бинарь.

### У BSD `sed` нет `\b`

**Симптом.** Первый проход переименования молча оставил половину вхождений.

**Причина.** У BSD `sed` нет `\b`. Помните об этом всякий раз, когда скрипт должен работать и на macOS,
и на Linux.

### macOS позволяет bind на конкретный адрес рядом с wildcard

**Симптом.** Проверка портов в `owlab doctor` рапортовала все порты свободными, пока `up` падал с
«address already in use».

**Причина.** Проверка опрашивала `127.0.0.1`.

**Решение.** Теперь опрашивается `0.0.0.0` — то, на что биндится Docker.

### Установленный QEMU, про который owlab говорил, что его нет

**Симптом.** На Windows `winget install SoftwareFreedomConservancy.QEMU` отрабатывает, и
`C:\Program Files\qemu\qemu-system-x86_64.exe` на месте. owlab сообщает, что не нашёл его.

**Причина.** Ни официальный установщик, ни winget не кладут QEMU в `PATH`, а owlab смотрел только туда.
Быть вне `PATH` — нормальное состояние правильной установки на Windows. То есть owlab объявлял
сломанной исправную машину.

**Решение.** owlab смотрит сначала в `PATH`, потом в каталоги установщиков:

- `%ProgramFiles%\qemu`
- `%LOCALAPPDATA%\Programs\qemu`
- каталог приложения scoop
- каталог chocolatey

`owlab doctor` печатает выбранные бинарь и `qemu-img`. `OWLAB_QEMU` по-прежнему перекрывает оба.

`qemu-img` берётся рядом с эмулятором, а не из `PATH`, по той же причине и ещё по одной. Оба должны быть
из одной установки: `qemu-img` от другого QEMU может записать qcow2, который эмулятор откажется читать.

### VM, которая «стартовала» на Windows и не ответила

**Симптом.** `owlab up` сообщал, что роутер поднимается, потом отваливался по таймауту ожидания ssh. В
логах ничего, потому что лога не было.

**Причина.** Их две, и обе невидимые:

1. QEMU получал `-object rng-random,filename=/dev/urandom`. На Windows нет `/dev/urandom`, и QEMU
   выходил до старта гостя.
2. Этот отказ нельзя было увидеть. На Windows QEMU запускается, а не выполняется до конца. Поэтому
   `Start` возвращал успех для уже мёртвого процесса, а его stderr уходил в никуда.

**Решение.**

- Теперь на Windows там `rng-builtin`: тот же virtio-rng для гостя и никакого символьного устройства,
  которого у хоста нет.
- owlab выжидает, замечает уже завершившийся QEMU и показывает, что тот сказал.

### Роутер, умиравший вместе с терминалом

**Симптом.** На Windows закрытие окна PowerShell уносило с собой запущенную VM.

**Причина.** Дочерний процесс, запущенный обычным образом, попадает в консольную группу родителя. При
закрытии окна он получает `CTRL_CLOSE_EVENT`. На unix QEMU уже отцеплен через `-daemonize`; на Windows
такого флага нет.

**Решение.** `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`. Вторая половина заодно означает, что Ctrl-C
во время `owlab up` прерывает ожидание, а не роутер.

### WHPX — не гарантия

**Симптом.** На Windows VM с `whpx` не грузится или виснет на середине, а тот же образ работает в
другом месте.

**Причина.** Аппаратное ускорение на Windows идёт через Hyper-V, и на части машин оно отказывает.

**Решение.** Задайте `OWLAB_ACCEL=tcg`, чтобы включить трансляцию. Это примерно на порядок медленнее и
работает всегда. Выясните, с чем из двух вы имеете дело, до того как отлаживать что-либо ещё.

## Загрузка упала

### `503 Service Unavailable (the server is failing, not refusing …)`

**Причина.** Сервер загрузок или GitHub сбоил и продолжал сбоить на протяжении всех повторов owlab
(4 попытки примерно за 14 секунд). С `owlab.yaml` всё в порядке.

**Решение.** Запустите команду позже. Для GitHub загляните на
[githubstatus.com](https://www.githubstatus.com).

То же относится к этим сообщениям:

| Сообщение | Что за ним стоит |
|---|---|
| `unreachable after 4 attempts (a network or server outage …)` | таймауты, сбои DNS и отказы в соединении |
| `the server sent nothing for 1m0s` | пакет не из фидов или комплаенс-файл, сервер которого замолчал |
| `reading the body: unexpected EOF` | оборвавшаяся загрузка |

Каждая попытка качает файл целиком заново.

### `404 Not Found` на образ, rootfs или пакет

**Причина.** Сервер ответил, и файла там нет. На 404 owlab спрашивает один раз.

**Решение.** Проверьте номер релиза и target в `owlab.yaml`. Релиз может ещё не публиковать такой
образ, или URL внефидового пакета неверен.

### `… did not answer (…); building <id> from the rootfs tarball … instead of <image>`

Это не ошибка. Реестр базового образа роутера отклонил соединение, не ответил вовремя или отвечал 5xx
либо 429 все 4 попытки. Этот реестр — Docker Hub для `openwrt/rootfs` по умолчанию или тот, что указан
в `image:`.

owlab собрал роутер из rootfs-tarball его релиза, а это тот же rootfs.

- Сборка идёт дольше, потому что слои от сборки на образе не переиспользуются.
- У образа честная платформа таргета (`linux/arm64` вместо `linux/aarch64_generic`).
- Следующий запуск снова спросит реестр.

**Если это видно при каждом запуске.** Машина, которая ходит на Docker Hub только через
`registry-mirrors` движка, видит это каждый раз: owlab обращается к `registry-1.docker.io` сам. Укажите
зеркало в `image:`, чтобы остаться на пути через образ. Прокси из `HTTPS_PROXY` owlab тоже использует.

**Если написано `… and neither did the rootfs tarball (…); leaving <id> on <image> for the engine …`.**
Та же проверка не достучалась и до сервера загрузок; так выглядит машина без сети. owlab оставляет образ
движку, как и до этой проверки. Движок скачает его через свой прокси или зеркало либо соберёт из копии
и слоёв, которые у него есть. Если не сможет ни того, ни другого, сборка упадёт на pull и назовёт

## Три поведения апстрима, которые стоит знать

### `kmods` должен остаться в списке фидов

**Симптом.** Без фида kmods `apk add luci-app-sqm` падает с `kmod-ifb (no such package)`.

**Причина.** Фид kmods разрешает `kmod-*`-**зависимости** обычных пакетов. Каждый широко скопированный
рецепт его вырезает, рассуждая, что загрузить оттуда всё равно ничего нельзя. Замерено — это неверно.

**Решение.** Оставьте фид kmods. Модули ставятся файлами и никогда не грузятся. Это стоит пары сотен
килобайт и жалобы kmodloader при загрузке.

### Фид должен быть запинен на точный точечный релиз

**Симптом.** Если направить rootfs 25.12.4 на фид 25.12.5, любая установка падает с `breaks: world[...]`.

**Причина.** apk записывает жёсткие пины в `/etc/apk/world` (`base-files=1707~4ccb782af7`).

**Решение.** owlab не переписывает фиды вообще — это самый простой способ не сломать это.

### Пин на точечный релиз всё равно движется

Пин фиксирует, из какого релиза вы ставите, но не то, какие байты этот релиз отдаёт.

- `releases/24.10.8/packages/` пересобирается на месте. Индекс `Packages` релиза, вышедшего месяцы
  назад, изменён вчера.
- Пакет может быть заменён под той же строкой версии.

Значит, индекс годен, только пока он свежий. Каждое место, которое его читает, обязано сначала его
обновить. См. [Индекс в образе старше слоя, который им пользуется](#индекс-в-образе-старше-слоя-который-им-пользуется).
