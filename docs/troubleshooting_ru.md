# Диагностика

[English](troubleshooting.md)

Всё здесь наблюдалось на работающем роутере. Каждая запись — симптом, причина и
что owlab с этим делает. Сгруппировано по тому, как оно выглядит, когда вы на
это напоролись: почти ничто здесь не похоже на свою причину.

## «Роутер вообще не отвечает на опубликованном порту»

### Интерфейс контейнера не попал ни в одну зону firewall

**Симптом.** `owlab up` пишет `did not answer on HTTP in time`. `curl` на
опубликованный порт не получает ничего — код выхода 52, пустой ответ, — при
том что внутри контейнера `uhttpd` слушает `0.0.0.0:80` и локальный запрос
отрабатывает. Замечено на ImmortalWrt: два роутера недоступны, а роутеры
OpenWrt на том же стенде работают.

```console
# uclient-fetch -O- http://127.0.0.1/cgi-bin/luci/
HTTP error 403                                              <- LuCI просит логин: так и надо
$ curl -o /dev/null -w '%{http_code}\n' http://localhost:18026/cgi-bin/luci/
000
```

То, что `owlab logs` обрывается на `- generating board file -`, ни о чём не
говорит: это последняя строка, которую печатает здоровый контейнер.

**Причина.** fw4 разворачивает зону в `iifname "<dev>" jump input_<zone>`, а
сам `<dev>` берёт из списка `network` зоны в момент сборки набора правил. Зона,
которая не разрешилась ни в одно устройство, не даёт строки jump вообще —
пакет доходит до конца цепочки input и попадает в `jump handle_reject`, то есть
получает TCP reset. С хоста это выглядит как пустой ответ, из соседнего
контейнера той же docker-сети — как `Connection refused`.

```console
# nft list ruleset | sed -n '/^\tchain input {/,/^\t}/p'
chain input {
        type filter hook input priority filter; policy drop;
        iifname "dummy0" jump input_wan     # ... и ни одной строки про br-lan
        jump handle_reject                  # значит, трафик lan приходит сюда
}
```

**Фикс.** `95_owlab-base` называет lan-устройство в этой зоне явно:
`list device 'br-lan'` рядом с уже имеющимся `network 'lan'`, `input ACCEPT` на
ней, а если в образе зоны для сети lan нет — она создаётся. `device` fw4 берёт
буквально, не спрашивая netifd, поэтому jump на месте независимо от того, что
netifd успел сделать к моменту чтения конфига; с сетью устройство
дедуплицируется — одна строка jump, измерено.

Firewall при этом остаётся включённым. fw4 в контейнере работает, а его
отключение спрятало бы целый класс настоящего поведения.

**Как проверить.** На роутере:

```console
# nft list ruleset | grep 'jump input_lan'
        iifname "br-lan" jump input_lan comment "!fw4: Handle lan IPv4/IPv6 input traffic"
```

### ssh закрывается сразу после открытия

**Симптом.** `ssh -p 12226 root@localhost` на роутер ImmortalWrt закрывается
мгновенно, при том что HTTP того же контейнера отвечает.

**Причина.** ImmortalWrt везёт в `/etc/config/dropbear` `option Interface 'lan'`,
а OpenWrt такого ключа не везёт — dropbear слушает один адрес вместо wildcard.
Измерено на одном стенде, `netstat -ltnp` внутри каждого контейнера:

```console
imm2512    tcp 0 0 192.168.163.5:22  LISTEN  2262/dropbear
owrt2512   tcp 0 0 0.0.0.0:22        LISTEN   889/dropbear
```

Этот адрес верен ровно до тех пор, пока netifd успевает поднять `lan` раньше
старта dropbear и пока ничего не приходит по другому адресу. Контейнер,
который пересоздают так часто, ни того ни другого не обещает.

**Фикс.** `95_owlab-base` удаляет ключ, и dropbear слушает `0.0.0.0:22` на обоих
дистрибутивах.

**Как проверить.** `netstat -ltn` внутри контейнера должен показать `0.0.0.0:22`.

## «Роутер отдаёт LuCI, но ничего не работает»

### procd джейлит сервисы, а контейнер не может построить джейл

**Симптом.** Роутер без DNS-сервера. Любой пакет, который настраивает dnsmasq
форвардить куда-то — указывая его на вспомогательный демон, — настраивает демона,
которого нет. `service dnsmasq status` говорит `not running`, а запуск внешне
проходит успешно.

**Причина.** procd джейлит изрядное число сервисов, а джейлу нужны неймспейсы,
создавать которые контейнеру не разрешено:

```console
$ ujail -n test -p -- /bin/true
jail: failed to clone/fork: Operation not permitted
```

procd считает это падением и респавнит, так что сервис сидит в вечном
crash loop, единственный след которого:

```
procd: Instance dnsmasq::cfg01411c s in a crash loop 6 crashes
```

Тот же бинарь, запущенный руками с тем же сгенерированным конфигом, работает
прекрасно — из-за этого причину и тяжело найти.

**Решение.** owlab убирает `/sbin/ujail` из образа контейнера. Без него procd
запускает сервис напрямую, поэтому это именно решение, а не обход.
Альтернатива — выдать контейнеру `CAP_SYS_ADMIN` — слишком близка к руту на
хосте, чтобы одноразовая коробка имела право её просить. Теряется граница
безопасности между сервисами внутри контейнера, который и так одна зона
доверия. Роутер `fidelity: vm` работает на своём ядре и джейлы сохраняет.

Так было во всех контейнерах owlab с самого начала. Не замечали, потому что
LuCI рисует страницы DHCP и DNS из конфига, а не из живого демона.

### Роутер сбрасывает каждое соединение

**Симптом.** TCP подключается и тут же получает reset — «connection reset by
peer» — при том что `uhttpd` жив и слушает `0.0.0.0:80`. Только на ImmortalWrt.

**Причина.** ImmortalWrt включает `flow_offloading` по умолчанию; правилу нужен
флоутейбл, а флоутейблу — `nf_flow_table` в работающем ядре. Где его нет, nft
отвергает **весь** ruleset, оставляя базовые цепочки с `policy drop` и без
единого перехода в зоны.

**Решение.** `95_owlab-base` создаёт флоутейбл в скрэтч-таблице и удаляет его, и
выключает настройку только если это не удалось. Сначала идёт `modprobe`: OpenWrt
не поставляет `modules.alias`, поэтому ядро не может автозагрузить модуль по
алиасу, который просит nft, и без этого проба врала на вполне способном роутере.

### LuCI отвечает, но исходящее не работает

**Симптом.** LuCI отдаёт 200, а любое исходящее соединение висит без ошибки.
`apk` выглядит зависшим.

**Причина.** mwan3 решает, что фиктивный WAN мёртв, и ставит
`2061: from all fwmark 0x3d00/0x3f00 blackhole`.

**Решение.** `95_owlab-base` останавливает и отключает mwan3 и watchcat.
Firewall в этот список намеренно не входит — fw4 работает, а его отключение
спрятало бы целый класс настоящего поведения.

## «Пакет установился и ничего не делает»

### `br-lan` не существовало

**Симптом.** Пакет ставится, запускается, рапортует об успехе и не пропускает
трафик. Его правила nft на месте, но не совпадают ни с чем.

**Причина.** `source_network_interfaces` по умолчанию `br-lan`, а lan
контейнера был голым `eth0`. То же верно для множества сниппетов firewall и
hotplug-скриптов.

**Решение.** lan контейнера — мост `br-lan` с `eth0` в портах. См.
[внутренности](internals_ru.md).

### Пакеты не из фида ставились в неверном порядке

**Симптом.** `ERROR: unable to select packages` на наборе пакетов, которые все
присутствуют.

**Причина.** Они складывались под собственными именами и ставились по глобу, то
есть по алфавиту. `luci-app-example` сортируется раньше `example-daemon`, от
которого зависит.

**Решение.** Складываются с номером и отдаются менеджеру одним набором, чтобы он
разрешал зависимости между ними сам.

### Конфликт файлов молча пропустил пакет

**Симптом.** `owlab up` печатает зелёный список; пакета нет. Только на
OpenWrt 24.10.

**Причина.** `luci-app-openclash` тянет `dnsmasq-full`, который ставит
`/etc/init.d/dnsmasq` и сталкивается с `dnsmasq`. ImmortalWrt везёт
`dnsmasq-full` из коробки, поэтому три роутера из четырёх не пострадали — один
и тот же конфиг давал на одном из них другой роутер.

**Решение.** `--force-overwrite`, и провал в `extra_packages` теперь фатален.

## «DNS сломан, а сеть цела»

### Движок не пропускает исходящий UDP на порт 53

**Симптом.** Демон со своим DNS-резолвером падает с
`initial rule-set: ... lookup github.com: context deadline exceeded` на
роутере, где `https://github.com` отвечает 200. Переключение на DoH не помогает
— `lookup dns.google` падает так же.

**Причина.** Часть движков (OrbStack, замерено) не форвардит исходящий UDP/53
вообще. Простой контейнер `alpine` там ведёт себя точно так же, значит дело в
движке, а не в OpenWrt. DoH падает тоже: такой демон сначала резолвит хост DoH
через обычный UDP-сервер на 53 порту, и только потом может использовать DoH.

**Решение.** В owlab не чинится. `owlab doctor` это проверяет и называет
собственный резолвер движка, который отвечает; пакету со своим резолвером надо
бутстрапиться через него, а DoH или DoT поднимать поверх TCP.

### Резолвер движка умирает посреди загрузки

**Причина.** Docker Desktop и WSL2 выдают `127.0.0.11`, реализованный
NAT-правилами, которые загрузка самого OpenWrt сбрасывает.

**Решение.** `/etc/resolv.conf` держит резолвер движка первым и дописывает
публичные за ним, с `options timeout:1`. Полная перезапись ломает OrbStack, где
публичные недостижимы; отсутствие дописывания ломает Docker Desktop. Чтение
файла перед перезаписью — то, что позволяет одному образу работать на обоих.

## «Wireless не поднимается»

### Всё, поставленное после загрузки, требует загрузки

**Симптом.** Радио существуют как настоящие phy и принимают команды `iw`, но
`ubus call network.wireless status` вечно показывает `up: false, pending: true`.
`wifi up` отвечает `Command failed: Not found`. Ни одна ошибка не называет
причину.

**Причина.** Три отдельные вещи одной формы — пакеты ставились на уже
загруженную систему:

- **procd** не запустил `wpad`, потому что на момент загрузки сервиса не было.
- **netifd** не загрузил поддержку wireless, потому что `/lib/netifd/wireless/*`
  читается при старте.
- **ubusd** не получил ACL от wpad, потому что `/usr/share/acl.d/` читается при
  старте. Без него hostapd — работающий под непривилегированным пользователем
  `network` — не может опубликовать свой ubus-объект, и скрипт настройки ждёт
  объект, который никогда не появится.

Последнее самое неочевидное: hostapd, запущенный **под root**, регистрируется
нормально, и это выглядит как проблема прав на сокет. Сокет world-writable;
воротами служат ACL ubusd.

**Решение.** Одна перезагрузка в конце провижининга VM, до применения оверлея.

### Детекция ставит каждое симулированное радио на 6 ГГц

**Симптом.** `iwinfo` показывает `Channel: 0 (unknown GHz)` и `HT Mode: null`.

**Причина.** `wifi config` выбирает самый высокий диапазон, который заявляет
phy, а симулированный phy заявляет все. При регуляторном домене `00` по
умолчанию 6 ГГц не разрешает почти ничего.

**Решение.** Фикстура `wifi` назначает первому радио 2.4 ГГц, второму 5 ГГц и
выставляет страну.

## «У меня работает»

### `--platform` всегда должен быть явным

Только `x86_64` нормализуется в настоящую OCI-платформу (`amd64`). Все
остальные таргеты публикуют нестандартную строку архитектуры
(`aarch64_generic`, `mips_24kc`), поэтому обычный pull на arm64-хосте падает с
`no matching manifest`.

У ImmortalWrt хуже: **каждый** тег в `immortalwrt/rootfs` помечен
`linux/amd64`, включая те, чьё содержимое aarch64. Их метаданными выбрать образ
нельзя вообще — поэтому owlab сам распаковывает тарбол и ставит честные
метаданные.

### busybox `ip` игнорирует `peer name`

**Симптом.** Контейнер в цикле перезапуска, в логе только
`SIOCGIFFLAGS: No such device`.

**Причина.** `ip link add eth1 type veth peer name eth1p` создаёт пару и
называет пир `vethN`. Поднятие `eth1p` после этого падает, а `set -e` уносит с
собой всю загрузку.

**Решение.** Имя пира вычитывается обратно из `ip -o link show`, и вся
косметика в entrypoint работает с выключенным errexit.

### Правка `images/` ничего не меняет, пока не пересобран бинарь

Контекст сборки вшит через `go:embed`. Работающий бинарь несёт собственную
копию. Это уже не раз давало ложный след — фикс «не работал», потому что в
образ он не попадал.

### У BSD `sed` нет `\b`

Первый проход переименования молча оставил половину вхождений. Стоит помнить
всякий раз, когда скрипт должен работать и на macOS, и на Linux.

### macOS позволяет bind на конкретный адрес рядом с wildcard

Проверка портов в `owlab doctor` опрашивала `127.0.0.1` и рапортовала все порты
свободными, пока `up` падал с «address already in use». Теперь опрашивается
`0.0.0.0` — то, на что биндится Docker.

### Установленный QEMU, про который owlab говорил, что его нет

**Симптом.** На Windows `winget install SoftwareFreedomConservancy.QEMU`
отрабатывает, `C:\Program Files\qemu\qemu-system-x86_64.exe` на месте, а owlab
сообщает, что не нашёл.

**Причина.** Ни официальный установщик, ни winget не кладут QEMU в `PATH`, а
owlab смотрел только туда. Быть вне `PATH` — нормальное состояние правильной
установки на Windows, то есть owlab объявлял сломанной исправную машину.

**Решение.** Сначала `PATH`, потом каталоги установщиков: `%ProgramFiles%\qemu`,
`%LOCALAPPDATA%\Programs\qemu`, каталог приложения scoop и каталог chocolatey.
`owlab doctor` печатает выбранные бинарь и `qemu-img`, а `OWLAB_QEMU`
по-прежнему перекрывает оба.

`qemu-img` берётся рядом с эмулятором, а не из `PATH`, по той же причине и ещё
по одной: оба должны быть из одной установки, иначе `qemu-img` от другого QEMU
запишет qcow2, который эмулятор откажется читать.

### VM, которая «стартовала» на Windows и не ответила

**Симптом.** `owlab up` сообщал, что роутер поднимается, потом отваливался по
таймауту ожидания ssh. В логах ничего — потому что лога не было.

**Причина.** Их две, и обе невидимые.

QEMU получал `-object rng-random,filename=/dev/urandom`. На Windows нет
`/dev/urandom`, и QEMU выходил до старта гостя. Теперь там `rng-builtin` — тот
же virtio-rng для гостя и никакого символьного устройства, которого у хоста нет.

И этот отказ нельзя было увидеть: на Windows QEMU запускается, а не
выполняется до конца, так что `Start` возвращал успех для уже мёртвого
процесса, а его stderr уходил в никуда. Теперь owlab выжидает, замечает уже
завершившийся QEMU и показывает, что тот сказал.

### Роутер, умиравший вместе с терминалом

**Симптом.** На Windows закрытие окна PowerShell уносило с собой запущенную VM.

**Причина.** Дочерний процесс, запущенный обычным образом, попадает в
консольную группу родителя и получает `CTRL_CLOSE_EVENT` при закрытии окна. На
unix QEMU уже отцеплен через `-daemonize`; на Windows такого флага нет.

**Решение.** `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`. Вторая половина
заодно означает, что Ctrl-C во время `owlab up` прерывает ожидание, а не роутер.

### WHPX — не гарантия

Аппаратное ускорение на Windows идёт через Hyper-V, и есть машины, где с `whpx`
VM не грузится или виснет на середине, тогда как тот же образ работает в другом
месте. `OWLAB_ACCEL=tcg` включает трансляцию: примерно на порядок медленнее и
работает всегда. Понять, с чем из двух имеешь дело, стоит до того, как
отлаживать что-либо ещё.

## Два поведения апстрима, которые стоит знать

### `kmods` должен остаться в списке фидов

Каждый широко скопированный рецепт его вырезает, рассуждая, что загрузить
оттуда всё равно ничего нельзя. Замерено — это неверно: фид kmods разрешает
`kmod-*`-**зависимости** обычных пакетов, и без него `apk add luci-app-sqm`
падает с `kmod-ifb (no such package)`. Модули ставятся файлами и никогда не
грузятся, что стоит пары сотен килобайт и жалобы kmodloader при загрузке.

### Фид должен быть запинен на точный точечный релиз

apk записывает жёсткие пины в `/etc/apk/world` (`base-files=1707~4ccb782af7`).
Направив rootfs 25.12.4 на фид 25.12.5, вы получите падение любой установки с
`breaks: world[...]`. owlab не переписывает фиды вообще — самый простой способ
не сломать это.
