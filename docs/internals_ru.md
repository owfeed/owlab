# Внутренности

[English](internals.md)

Как owlab устроен внутри и почему каждая часть ведёт себя именно так. Для тех, кто меняет owlab.
Для работы с ним это знать не нужно — начните с [ранбука](runbook_ru.md).

- **Один бинарь на Go, без демона.** Состояние лежит только в `.owlab/` проекта и в одном кеше образов.
- **Два тира, выбор на каждый роутер.** `basic` — контейнер с procd в качестве PID 1. `vm` — QEMU как
  обычный процесс хоста.
- **К роутеру обращаются только через проброшенные порты**, никогда по IP моста. `localhost` работает
  одинаково на любом хосте.
- **Возможности проверяются пробой и никогда не выводятся из платформы.** Догадки по ОС в этом проекте
  уже ошибались.
- **Правка чего угодно под `images/` требует пересборки бинаря.** Бинарь несёт свою копию.

## Архитектура

owlab — один бинарь на Go. Он несёт контекст сборки образов внутри себя. Для контейнерных роутеров
он генерирует compose-файл, для VM запускает QEMU напрямую. Демона нет. Состояния за пределами
каталога проекта и одного кеша образов тоже нет.

### Пакеты Go

```
cmd/owlab/           CLI: файл на группу команд
internal/config/     owlab.yaml — разбор, слияние, валидация
internal/compose/    генерация compose-файла и контекста сборки
internal/qemu/       тир VM: образы, ускорители, жизненный цикл, провижининг
internal/sync/       копирование исходников в роутеры, перезагрузка LuCI
internal/sshx/       выполнение команд на роутере по ssh
internal/upstream/   опрос серверов загрузки
internal/engine/     определение движка контейнеров и его возможностей
internal/dockercli/  вызовы docker / docker compose
internal/pkgmgr/     сборка командной строки apk/opkg
internal/tarx/       сборка tar-потоков, которые уезжают в роутеры
images/              контекст сборки, вшитый в бинарь
```

`pkgmgr` и `tarx` существуют потому, что оба тира делают одно и то же разными средствами.
Расхождение между тирами здесь было бы багом, который никто не увидит.

- `pkgmgr` знает, что `--allow-untrusted` есть только у apk. Ещё он знает, что отсутствующий в фиде
  пакет должен стоить только этого пакета, роутер при этом живёт.
- `tarx` знает правила заголовков. Он пишет формат GNU, потому что дерево LuCI выходит за 100 байт,
  отведённых USTAR.

`images/` вшивается через `//go:embed all:images`. Разработчик, запускающий `owlab up` в собственном
пакете LuCI, копии этого репозитория не имеет и иметь не должен.

Префикс `all:` обязателен. В оверлее лежат файлы `/etc/uci-defaults`, а без префикса `go:embed` молча
пропускает имена, начинающиеся с `_` или `.`.

Оверлей — это `images/rootfs-extra/`. `images/Dockerfile` копирует его в `/` образа, а в VM он
заливается при провижининге.

| Файл | Путь в этом репозитории |
|---|---|
| `95_owlab-base` | `images/rootfs-extra/etc/uci-defaults/95_owlab-base` |
| `96_owlab-fixtures` | `images/rootfs-extra/etc/uci-defaults/96_owlab-fixtures` |
| Профили фикстур, среди них `60-wifi.sh` | `images/rootfs-extra/usr/share/owlab/fixtures/` |
| Entrypoint контейнера | `images/rootfs-extra/usr/lib/owlab/entrypoint.sh` |

**Правка чего угодно под `images/` требует пересборки бинаря.** Работающий бинарь несёт свою копию.
Изменение файла на диске не меняет ничего, пока снова не отработает `go build`. Это уже не раз давало
ложный след.

### Как проходит команда

`owlab up`:

1. `config.Find` идёт вверх от рабочего каталога в поисках `owlab.yaml`, так что работает любой
   подкаталог.
2. `config.Load` разбирает файл и валидирует. По пути он вливает `defaults:` в каждый роутер,
   применяет арифметику пакетов поверх стокового набора и резолвит `arch: auto` под хост. После этого
   `Router` полностью определён: ниже по течению никто ничего не вычисляет заново.
3. Если хоть один роутер контейнерный, owlab проверяет Docker и определяет движок. Проект, где все
   роутеры `fidelity: vm`, Docker не трогает вовсе. Требовать его было бы требованием, выдуманным
   owlab.
4. Роутеры делятся по тирам.
   - У контейнеров сначала проверяется базовый образ. `resolveBaseImages` шлёт `HEAD` манифеста в
     реестр образа. Он переводит роутер на rootfs-tarball, если тега нет или если реестр не отвечает,
     а сервер загрузок tarball отдаёт.
   - Затем контейнеры идут через `compose.Prepare`. Он пишет `authorized_keys` и compose-файл и
     распаковывает контекст сборки. Он качает rootfs-tarball, пакеты не из фидов и комплаенс-бандл
     собираемых роутеров. Дальше идут `docker compose build` и `up`.
   - VM идут через `qemu.New(...).Start` и, если диск новый, `Provision`.
5. owlab опрашивает оба тира на проброшенном HTTP-порту, пока не ответит LuCI. Роутер «поднялся»,
   когда отдаёт uhttpd. Старта процесса для этого мало: procd должен пройти всю загрузку и применить
   uci-defaults.

#### У `Prepare` две половины

Какая из них нужна команде, имеет значение.

| Половина | Что делает | Нужна сеть |
|---|---|---|
| `compose.Render` | пишет compose-файл и больше не трогает ничего; контекст не сносит | нет |
| `compose.Materialize` | сносит и перезаписывает контекст сборки, а затем качает то, что в него кладётся, для переданных ему роутеров и только для них | да |

`up` и `context` нужны обе. `down`, `logs` и `up --no-build` — только `Render`. Это не
микрооптимизация. Без этого остановка роутера или чтение его лога падали бы на машине без сети, на
файлах, с которыми ничего собирать и не собирались.

Dockerfile копирует `extra/<id>/` и `compliance/<id>/` того роутера, который собирает. Так что слои
роутера хешируют только его файлы и не меняются от выбора роутеров.

#### Что проверяет `up --no-build`

`up --no-build` запускает образы, которые уже есть у движка. Он пропускает проверку реестра,
`Materialize` и `compose build`.

Каждый образ, собранный `compose build`, несёт метку `org.owlab.inputs` — это `compose.Inputs`.
Это дайджест от:

- версии и VCS-ревизии этого owlab;
- встроенного контекста сборки;
- build args и платформы;
- релиза и URL его rootfs-тарбола;
- URL из `extra_packages`.

У двух сборок одного коммита с разными незакоммиченными правками он общий. `up --no-build` запускает
образ, только если метка совпадает с этим дайджестом для конфига, прочитанного сейчас.

Того, что фиды отдали во время сборки, в дайджесте нет и быть не может. Одни и те же входы, собранные
с разницей в неделю, ставят пакеты своей недели.

### Шов между тирами

Всё, что выше транспорта, написано один раз. `cmd/owlab/transport.go` описывает то, что различается
от роутера к роутеру:

```go
type tier interface {
	Stream() (stream, error)                                  // выполнить скрипт; stdin, stdout, stderr раздельно
	Interactive(ctx context.Context, command ...string) error // отдать терминал
	State(ctx context.Context) string                         // одно слово для `owlab status`
}
```

Реализаций две: `containerTier` поверх `docker exec` и `vmTier` поверх ssh. Sync, `post_sync`,
`install`, сброс кешей LuCI, `shell` и таблица статуса написаны против этого интерфейса. Только две
реализации знают, какой роутер на том конце.

#### Почему `Stream` принимает поток

`Stream` принимает stdin как поток и держит stdout и stderr раздельно. `owlab exec` передаёт свой
stdin дальше, а у него нет длины (`yes | owlab exec r -- head -1`).

Байтовый `sync.Exec`, которым пользуются sync, install и проверки, собирается из `Stream` в
`execFor`. Так что способ выполнить скрипт у каждого тира по-прежнему один.

Тир добавляет `docker exec -i` (или отдаёт ssh stdin), только когда stdin не nil. Tty он никогда не
выделяет: tty превращает LF в CRLF в данных из пайпа.

#### Почему пакетных операций нет в интерфейсе

`build`, `up`, `down` и `logs` в интерфейс намеренно **не входят**. Они пользуются `splitTiers` и
разбираются с каждым тиром на его условиях.

<details>
<summary>Рассуждение</summary>

Compose работает сразу по всему проекту и именно из этого получает снос сети. Тир VM поднимает по
процессу хоста на роутер. Загонять `build`, `up`, `down` и `logs` в пороутерную форму значило бы
превратить одну сборку в N. Ещё это лишило бы `down` того, что делает его сносом.

</details>

#### Почему передача файлов — это tar на stdin

Файлы передаются tar-ом на stdin, без `docker cp` и `scp`. Это единственная операция, которая есть у
обоих транспортов. dropbear не везёт sftp-server, так что `scp` против VM потребовал бы доставить
пакет ради этого.

### Что генерируется и куда

```
<проект>/.owlab/
  compose.yaml        генерируется каждый запуск; не редактировать
  context/            распакованный вшитый контекст сборки
  cache/              пакеты не из фидов и комплаенс-файлы
  authorized_keys     публичные ключи разработчика, склеенные
  vm/<id>/            каталог на VM-роутер — диски, консоль, pidfile
```

`.owlab/` owlab сам добавляет в gitignore при первом использовании.

Загрузочные образы VM лежат **не** здесь. Они идут в пользовательский кеш
(`~/Library/Caches/owlab/images` на macOS). Каждый весит четверть гигабайта, и их разделяют все
проекты на машине, которые грузят тот же релиз.

Записи каждого роутера идут в qcow2-оверлей внутри проекта. Так что кешированный образ остаётся
read-only, и одна закачка обслуживает всё.

### Два правила, определившие дизайн

**Никто не обращается к роутеру по IP моста.** Только проброшенные порты. Подсеть моста контейнера
маршрутизируется с хоста на нативном Linux и внутри WSL2. На Docker Desktop для Mac и Windows она не
маршрутизируется. Так что `http://localhost:<port>` — единственная форма, работающая везде одинаково.

**Возможности проверяются пробой и никогда не выводятся из платформы.** Каждое из этого в истории
проекта было угадано из ОС неверно:

- какой ускоритель есть у QEMU;
- может ли ядро создать флоутейбл;
- пропускает ли движок UDP.

Homebrew-овский `qemu-system-x86_64` на Apple Silicon сообщает только `tcg`, тогда как
`qemu-system-aarch64` из той же бутылки умеет `hvf`. Ни одно правило про macOS этого не угадает.

## Тиры

Их два: `basic` и `vm`. Тир выбирается на каждый роутер. Для большинства работы с LuCI хватает
дешёвого, а дорогой не бесплатен.

| | `basic` | `vm` |
|---|---|---|
| что это | контейнер: стоковый rootfs, procd в качестве PID 1 | QEMU как обычный процесс хоста, настоящее ядро OpenWrt |
| модули ядра | не грузятся | грузятся |
| настоящие радио | нет | два phy `mac80211_hwsim` по умолчанию |
| настоящий оверлей | нет | squashfs `/rom` плюс пишущий оверлей |
| состояние | — | диск и есть роутер |
| цена | дёшево | около 100 с в первый раз, около 18 с на каждый следующий старт |

### `basic` — контейнер

Стоковый rootfs релиза с procd в качестве PID 1.

`CMD ["/sbin/init"]` не обсуждается. Запуск `uhttpd` напрямую вместо системы инициализации роняет LuCI
с `left-hand side expression is null` в `runtime.uc:133` (openwrt/luci#8726). Диспетчер читает данные
платы из procd через ubus, и обойти это нечем. Система инициализации и есть продукт.

Что работает:

- ubus, rpcd, uhttpd, netifd, uci, весь LuCI;
- `apk` и `opkg`;
- nftables и fw4 (замерено: 311 правил на OpenWrt, 324 на ImmortalWrt);
- те возможности netfilter, которые есть у ядра **движка**. tproxy на OrbStack и на большинстве
  Linux-хостов работает.

Что не работает: загрузка модулей ядра, `sysupgrade`, настоящие радио, DSA.

Сильнее всего кусают два контейнерных поведения: джейлы procd и исходящий UDP. См.
[диагностику](troubleshooting_ru.md).

### `vm` — настоящее ядро OpenWrt

QEMU как обычный процесс хоста, вне контейнера.

В этом весь замысел. Вложенному QEMU нужен `/dev/kvm`, проброшенный в контейнер. Docker Desktop не
даёт его ни на macOS, ни на Windows — то есть ровно на тех хостах, которым этот тир нужнее всего.

Запуск нативно переворачивает задачу. На Apple Silicon гость aarch64, ускоритель hvf. Роутер грузится
за девять секунд без вложенной виртуализации, без минимальной версии macOS и без особого железа.

Что он добавляет:

- **Модули ядра грузятся.** `apk add kmod-nft-tproxy`, и `lsmod` показывает `nft_tproxy`. Ради этого
  тир и существует.
- **Настоящие радио.** Два phy `mac80211_hwsim` по умолчанию. На них работает hostapd, `iwinfo` отдаёт
  сигнал, шум и мощность. Страницы Wireless в LuCI показывают сам роутер. В контейнере они рисуются только из конфига.
- **Настоящий оверлей.** squashfs `/rom` плюс пишущий оверлей, так что `firstboot` и `jffs2reset`
  ведут себя как на железе.
- **Переживающее состояние.** Диск и есть роутер: `owlab down` — выключение, `--rebuild` — сброс к
  заводским.

Чего он стоит: около 100 секунд в первый раз (закачка, extroot, пакеты, две перезагрузки). Дальше —
около 18 секунд на каждый старт.

Как он устроен — в разделе [Тир VM](#тир-vm) ниже.

### Убранный тир

В раннем дизайне был третий тир, `full`: контейнер с настоящими phy `mac80211_hwsim`, перенесёнными из
ядра **хоста**. Его убрали. Он был недоступен на тех машинах, которым больше всего нужно что-то лучше
контейнера. А когда тир VM получил настоящие радио на любом хосте, `full` стал вторым, худшим способом
добыть то же самое.

<details>
<summary>Почему <code>full</code> не работал на большинстве хостов</summary>

Он требовал Linux-ядра, которым разработчик управляет.

| Хост | Мог ли |
|---|---|
| нативный Linux, WSL2 | да |
| Colima, Lima | после установки `linux-modules-extra` |
| Docker Desktop для macOS | никогда: его ядро LinuxKit собрано с невыставленным `CONFIG_CFG80211` |
| OrbStack | нет: у его ядра нет беспроводного стека и нет поддерживаемого способа добавить модули |

Все кандидаты (`mac80211_hwsim`, `virt_wifi`, `vwifi`, `wmediumd`) лежат поверх cfg80211.
`CONFIG_IKHEADERS` тоже не выставлен, так что собрать модуль на месте — тоже не выход. Единственный
проект, который это делал, мёртв с 2019 года.

То есть тир был бы недоступен ровно на тех машинах, которым больше всего нужно что-то лучше
контейнера. Как только VM получил настоящие радио на **любом** хосте, остался второй, худший способ
добыть то же самое на подмножестве хостов. Два тира, различающихся по существу, лучше трёх, где один —
оговорённая версия другого.

</details>

## Сеть

### Как достучаться до роутера

Всегда через проброшенные порты: `http://localhost:<http>` и `ssh -p <ssh> root@localhost`.

Подсеть моста контейнера маршрутизируется с хоста на нативном Linux и внутри WSL2. На Docker Desktop
для Mac и Windows она не маршрутизируется, и `--network host` и `macvlan` там тоже не работают. Поэтому
ничто в owlab не обращается к роутеру по IP моста, и одна и та же команда работает на любом хосте.

Для VM порты — это записи `hostfwd` в QEMU, ведущие на LAN-сторону гостя. Порядок двух сетевых карт
там и есть весь замысел; см. [тир VM](#тир-vm) ниже.

### `br-lan`

lan контейнера — мост с именем `br-lan`, у которого `eth0` единственный порт.

Он нужен, потому что его ждут пакеты. Каждый таргет OpenWrt больше чем с одним ethernet-портом строит
`br-lan`, поэтому пакеты и скрипты ссылаются на него по имени. Список интерфейсов в конфиге пакета по
умолчанию обычно именно он. Так же и во множестве сниппетов firewall, hotplug-скриптов и форумных
рецептов.

На роутере, чей lan был голым `eth0`, всё это применялось в никуда. Ошибки не было, просто функция не
работала.

Entrypoint настраивает мост до старта procd:

- **Мост забирает MAC у `eth0`.** Это его единственный и потому самый младший по MAC порт. Так что
  veth-пир движка продолжает доставлять по тому же адресу, и на стороне хоста никто ничего не замечает.
- **Собственный адрес `eth0` сбрасывается.** Порт моста не может нести L3. Оставленный адрес даёт ядру
  connected-маршрут через интерфейс, который больше не передаёт.
- **`OWLAB_LAN_BRIDGE=0` возвращает lan на `eth0`.** Это единственный интерфейс, который не имеет права
  сломаться. Движку, которому не нравится мостить свой veth, до работоспособности должна оставаться
  одна переменная. Пересборка образа для этого — слишком много.

### Почему сетевой конфиг пишет entrypoint

Сетевой конфиг пишет entrypoint из-за момента запуска. Именно поэтому это не скрипт `uci-defaults`.

К тому времени, когда выполняются `/etc/uci-defaults/*`, `eth0` уже опущен и очищен. uci-default не
может прочитать адрес, который выдал движок, потому что читать уже нечего.

Затем `/bin/config_generate` пишет собственный конфиг из `/etc/board.json`. На x86 и armsr это
`br-lan` с зашитым 192.168.1.1. netifd его применяет, и адрес движка исчезает. Контейнер становится
недостижим, и консоли, из которой можно чинить, нет.

<details>
<summary>Как entrypoint обезоруживает <code>config_generate</code> и почему опрашивает адрес</summary>

Защита `config_generate` — это `[ -s /etc/config/network -a -s /etc/config/system ] && exit 0`.
Поэтому запись **обоих** файлов в entrypoint и есть то, что его обезоруживает. Отсюда и
`/etc/config/system` в образе, хотя ничего интересного в нём нет: пустой или отсутствующий снова
взводит генератор.

Адрес опрашивается до десяти секунд, одного замера мало. Движки запускают процесс контейнера и
настраивают его интерфейс параллельно. Так что `eth0` может быть ещё голым, когда PID 1 начинает
работу, — надёжно так на перезапуске или нагруженной машине.

Один замер, ничего не нашедший, не безобиден. Конфиг не запишется, отработает `config_generate`, и
коробка поднимется на 192.168.1.1 без маршрута к ней.

</details>

### DNS

`/etc/resolv.conf` держит резолвер движка первым и дописывает публичные за ним. Ни одна половина не
лишняя, потому что движки расходятся в том, какая работает:

| Движок | Какой резолвер выдаёт | Что ломается без второй половины |
|---|---|---|
| Docker Desktop, WSL2 | встроенный `127.0.0.11`, реализованный NAT-правилами, которые загрузка самого OpenWrt сбрасывает | он перестаёт отвечать посреди загрузки, так что в списке должно быть что-то ещё |
| OrbStack | резолвер, продолжающий работать после загрузки | прямой UDP/53 в интернет не форвардится вообще, так что одни публичные резолверы не разрешают ничего |

Перезапись файла так, как хочет случай Docker Desktop, оставляет контейнер на OrbStack без DNS. Чтение
файла перед перезаписью — то, что заставляет один образ работать на обоих.

`options timeout:1` там для того, чтобы умерший посреди загрузки резолвер стоил одну секунду вместо пяти.

### Исходящий UDP на порт 53

Часть движков не форвардит его вообще. Замерено на OrbStack:

```console
$ owlab exec pk -- 'dig +short github.com @127.0.0.11; dig +short github.com @8.8.8.8'
140.82.121.4
;; communications error to 8.8.8.8#53: timed out
```

Простой контейнер `alpine` на том же движке ведёт себя точно так же. Значит, дело в движке, OpenWrt
здесь ни при чём, и owlab это не чинит. TCP не затронут: `https://github.com` отвечает 200.

Это важно, потому что пакет со своим резолвером тогда не разрешает ничего и винит место назначения.
Такой демон падает с

```
initial rule-set: ... lookup github.com: context deadline exceeded
```

на роутере, где GitHub по https в порядке.

Решение всегда одно. Направьте бутстрап-резолвер пакета на собственный резолвер движка, который
отвечает, и поднимите поверх DoH или DoT по TCP. `owlab doctor` это проверяет через работающий роутер
и называет нужный резолвер.

### Flow offloading

ImmortalWrt включает его по умолчанию (`firewall.@defaults[0].flow_offloading` и `_hw`). OpenWrt
такого ключа не поставляет.

Правилу нужен флоутейбл, а флоутейблу — `nf_flow_table` в **работающем** ядре. Где его нет, nft
отвергает весь ruleset:

```
flowtable ft { ... Error: Could not process rule: No such file or directory
meta l4proto { tcp, udp } flow offload @ft;
```

Остаются базовые цепочки с `policy drop` и без переходов в зоны. Симптом — роутер, который завершает
TCP-рукопожатие и тут же сбрасывает соединение. При этом uhttpd жив и слушает `0.0.0.0:80`.
Рапортуется это как «connection reset by peer» против коробки, выглядящей совершенно здоровой.

`95_owlab-base` проверяет пробой и ничего не предполагает. Он создаёт флоутейбл в скрэтч-таблице и
удаляет его, и выключает настройку, только если это не удалось. Хост, который **умеет** офлоадить,
сохраняет конфигурацию своего дистрибутива. VM, чьё ядро собственное для OpenWrt, — тоже.

`modprobe` перед пробой нужен. OpenWrt не поставляет `modules.alias`, поэтому ядро не может
автозагрузить модуль по алиасу, который просит nft. Без `modprobe` проба врала на вполне способном
роутере.

### Сервисы, которые выключаются

`95_owlab-base` останавливает и отключает два сервиса. Каждый был замечен за тем, что роняет коробку:

- **mwan3** следит за WAN, решает, что фиктивный интерфейс мёртв, и ставит ip-правила, которые
  блэкхолят всё (`2061: from all fwmark 0x3d00/0x3f00 blackhole`). Симптом — роутер, отвечающий на
  LuCI, у которого висит любое исходящее соединение: `apk add` стоит вечно.
- **watchcat** перезагружается или переподключается по расписанию, когда считает сеть упавшей, а здесь
  он считает так всегда.

Они останавливаются и остаются установленными, поэтому их страницы в LuCI на месте.

Firewall в этот список намеренно не входит. fw4 работает, и его отключение спрятало бы целый класс
настоящего поведения.

## Пакеты

### Стоковый набор

Роутер вообще без `packages:` — это не голый rootfs. Это то, что установлено на серийном устройстве с
OpenWrt.

Список — собственные `DEFAULT_PACKAGES` и `DEFAULT_PACKAGES.router` OpenWrt из `include/target.mk`.
Сверху добавляется то, что firmware-selector ставит беспроводному роутеру с LuCI. Список сверен с
пакетами реального устройства (netcore n60 pro, mediatek/filogic). Он лежит в
`internal/config/packages.go`.

Бо́льшая его часть уже есть в апстримном rootfs-тарболе, так что установка обычно ничего не делает.
Перечисление всё равно имеет смысл: набор становится свойством owlab, и от тарбола, который
дистрибутив решил опубликовать, он не зависит. Так что форк с более тощим rootfs получает тот же
роутер.

От списка реального устройства есть два осознанных отступления.

**`libustream-mbedtls` не назван**, хотя в апстримном списке он есть. TLS-бэкенд — выбор времени
сборки, фиксированного имени у него нет. В каждом образе уже есть тот вариант, с которым он собран, и
просьба к ImmortalWrt 24.10 поставить mbedtls-вариант падает сразу.

**Ничего платформенного.** `fitblk`, `uboot-envtools`, `kmod-usb3`, `kmod-leds-gpio`,
`kmod-gpio-button-hotplug`, `kmod-crypto-hw-safexcel`, `kmod-mt7915e` и прошивки mt7986 описывают
разметку флеша, загрузчик, светодиоды и радиокремний одной коробки. Без этого железа они не работают, а
у контейнера нет своего ядра, чтобы их загрузить. Если разрабатываемому пакету нужен такой пакет на
диске для разрешения зависимости, добавьте его в проекте.

### Арифметика

Стоковый набор — **база** для `+`/`-`. Запасным вариантом для пустого списка он не служит. Именно
поэтому `packages: ["-ppp"]` значит то, что написано.

```yaml
defaults:
  packages: ["-ppp", "-ppp-mod-pppoe"]   # applied to the stock set
routers:
  - id: a
    packages: ["+luci-app-sqm"]          # applied to the result of the above
```

Список совсем без префиксов заменяет набор целиком. Явный список — это человек, который говорит, что
знает, чего хочет.

#### Один вызов, затем запасные пути

Набор ставится одним вызовом. Замерено на 74 именах luci-theme-footstrap на 24.10.8:

| Прогон | Вызов на пакет | Один вызов |
|---|---|---|
| первая установка | 81 с | 58 с |
| второй проход, всё уже стоит | 27 с | меньше одной |

Если вызов не прошёл, owlab убирает имя, которого нет в фидах, а на opkg — ещё и имя, которое даёт уже
стоящий пакет. Остальное запрашивается снова одним вызовом. Только если не прошло и это, каждый пакет
ставится отдельно, чтобы назвать те, что не встают.

#### Сбой сообщается и не фатален

Фиды различаются между релизами и между форком и апстримом. Поэтому имя, которого нет на 24.10, стоит
только этого пакета, образ целиком при этом собирается:

```
owlab: skip (not in this feed): luci-app-openvpn
```

Эта строка — для имени, которого в фиде нет. Например, снапшот-фид от 2026-10-20 не нёс
`luci-app-openvpn`.

Любой другой отказ, например конфликт файлов или зависимость, которой нет в фиде, печатает
собственный вывод менеджера пакетов. Затем печатается `owlab: FAILED to install <name>`, и сборка идёт
дальше без этого пакета.

Идти дальше не значит пропустить молча. Имя попадает в `/etc/owlab/packages-failed`. `owlab up`
читает этот файл с работающего роутера и сообщает о нём перед выходом с кодом 1 — так же, как для
`extra_packages` ниже. Если бы слой вместо этого обрывался, отменились бы все остальные роутеры сборки.

Два вида сбоев разбираются внимательнее, потому что иначе каждый попал бы в кеш:

- **Загрузка повторяется**: 4 попытки с паузами 2, 4 и 8 с, по расписанию `internal/netx`. Как только
  слой выходит с 0, buildkit его хранит. Каждый `owlab up` после оборванной закачки отдавал бы тот же
  неполный роутер.
- **Имя, не найденное после обновления, в котором какой-то фид не ответил, — сбой**, потому что этот
  фид мог его нести. Исключение — когда не ответил только индекс kmods. Снапшот-образ старше окна
  ядер фида теряет его на каждой сборке, а в нём есть только пакеты `kmod-*`.

### `extra_packages` — всё, чего нет в фидах

Ваш собственный пакет или что угодно, опубликованное на GitHub Releases.

У каждой записи два URL, потому что менеджеры не делят схему именования. Один и тот же релиз публикует
`luci-theme-footstrap-0.11.5-r1.apk` и `luci-theme-footstrap_0.11.5-r1_all.ipk`.

Пять вещей определяют, как они ставятся. Каждая из них сначала была багом.

**Скачивание на хосте.** В стоковом rootfs OpenWrt нет `curl`, а его busybox `wget` не умеет TLS. Так
что скачивание внутри образа зависело бы от того, какие пакеты пользователь случайно выбрал. На хосте
оборванная закачка ещё и сообщается как она есть. В образе она стала бы непонятной ошибкой менеджера
пакетов в трёх слоях от начала сборки.

**Порядок сохраняется.** Файлы кладутся с номерами (`00-`, `01-`), потому что образ ставит то, что
вернул glob, а glob сортирует по алфавиту. Эти пакеты зависят друг от друга. `luci-app-example`
требует `example-daemon` и сортируется раньше него, и apk отказывает сразу с
`unable to select packages`.

**Все одной командой.** Получив весь набор, менеджер пакетов разрешает зависимости между ними, и
порядок перестаёт иметь значение. Повтор ниже идёт по одному файлу и снова опирается на порядок
раскладки.

**`--force-overwrite`.** Их зависимости регулярно заменяют файл, которым уже владеет стоковый образ:

```
check_data_file_clashes: Package dnsmasq-full wants to install file
/etc/init.d/dnsmasq. But that file is already provided by package dnsmasq
```

На настоящем роутере эта проверка — полезная защита. Здесь замена — ровно то, о чём просили.
ImmortalWrt уже ставит `dnsmasq-full`. Без этого флага один и тот же конфиг давал на OpenWrt 24.10
другой роутер, чем на остальных трёх.

**Сбой здесь не проглатывается и не фатален**, в отличие от имени из фида.

- **Не проглатывается:** эти пакеты названы по URL. Разработчик сказал «поставь этот файл». Сборка,
  отрапортовавшая успех без него, отдала бы роутер, в котором тихо нет того, на чём он проверяет свою
  работу.
- **Не фатален:** раньше один негодный файл убивал все остальные роутеры лаборатории. См. ниже.

Поэтому набор ставится целиком, а если не вышло — по одному файлу. То, что так и не встало,
записывается в `/etc/owlab/extras-failed`. `owlab up` читает этот файл с работающего роутера,
сообщает о нём под своей таблицей и выходит с ненулевым кодом. `owlab test` на нём падает как на шаге
`extra_packages`.

Именно запись делает терпимость честной. Лог сборки уезжает вверх, а роутер, запущенный из
кешированного образа, его вообще не печатал.

<details>
<summary>Почему от фатального сбоя отказались (замерено 2026-09-04)</summary>

Фатальный сбой был первым ответом и стоил больше, чем спасал. `docker compose build` кладёт все
роутеры в один solve buildkit. buildkit отменяет solve на первой упавшей цели. Так что один негодный
файл убивал все остальные роутеры лаборатории.

Замерено 2026-09-04 на стенде из трёх роутеров:

- opkg выходит с 255 на неразрешимой зависимости;
- apk выходит с 27 на `unable to select packages`;
- оба оставляли соседей в `CANCELED`. Причина — `set -eu`, менеджер пакетов здесь ни при чём.

Ручки тоже нет: ни у `docker compose build`, ни у `docker buildx bake` нет `--keep-going`.

</details>

#### Подписи не проверяются

Они ставятся **без проверки подписи**. Проекты, публикующиеся так, обычно подписывают usign и кладут
`.sig` рядом с артефактом. Проверка требует их публичного ключа, а это ровно то решение о доверии,
которое дев-контейнер не должен принимать за пользователя.

Считайте всё, поставленное так, доверенным только по URL. Пиньте точный релиз вместо ссылки на
`latest`. Не переносите этот приём никуда, что уезжает в продакшн.

### Фиды

**Они остаются ровно такими, какими их привёз rootfs.** Вырезанная строка `kmods` ломает установку, а
любая перезапись фида рискует сломать пин версии.

#### Почему строка `kmods` остаётся

Соблазнительно вырезать строку `kmods`. Она запинена на точный хеш сборки ядра, и загрузить оттуда
ничего нельзя, потому что работающее ядро принадлежит движку. Каждый широко скопированный рецепт для
контейнера её вырезает.

Замерено — это неверно. Фид kmods разрешает `kmod-*`-**зависимости** обычных пакетов. Без него
`apk add luci-app-sqm` падает с `kmod-ifb (no such package)`.

Модули ставятся файлами и просто не грузятся. Это стоит пары сотен килобайт и жалобы kmodloader при
загрузке. Это куда дешевле менеджера пакетов, не способного поставить половину фида.

#### Почему фиды не переписываются

Оставить их в покое — это ещё и то, что сохраняет пин версии верным. apk записывает жёсткие пины в
`/etc/apk/world` (`base-files=1707~4ccb782af7`). Поэтому rootfs 25.12.4, направленный на фид 25.12.5,
роняет любую установку с `breaks: world[...]`. Фиды, приехавшие в образе, уже называют его точный
точечный релиз, и любая перезапись рискует это сломать.

#### Пиньте точный точечный релиз

Практический вывод для проекта: **пиньте точный точечный релиз.**

Rootfs и фид снапшота пересобираются ежедневно и независимо. Они расходятся в течение суток, и
библиотека может за это время сменить ABI. 2026-10-20 `ucode-mod-html` из фида требовал `libucode`, с
которой `ucode` образа не слинкован. Установка по имени оставила LuCI с ответом 502.

Поэтому на скользящем релизе owlab запускает `apk upgrade` после обновления индекса и до любой
установки. Так весь образ подтягивается к фиду, из которого сейчас будет ставить.

Точечный релиз не обновляется никогда. Его ABI не движется, и его пользователь ставит пакеты без
обновления.

Роутер на снапшоте всё равно не воспроизводим, и `owlab doctor` предупреждает, когда роутер называет
`snapshot`.

### apk и opkg

Менеджер — свойство дистрибутива. Номер версии его не определяет. OpenWrt переключился в 25.12. Форк
может отслеживать 25.12 и всё равно собираться с opkg (Kwrt так и делает, с
`# CONFIG_USE_APK is not set`).

Поэтому порядок такой:

1. что сказано в конфиге;
2. что пинит дистрибутив;
3. правило версии OpenWrt.

Вывод менеджера из одного номера релиза выдал бы такому роутеру команды apk и уронил бы каждую
установку.

## Тир VM

Настоящее ядро OpenWrt, которое QEMU грузит как обычный процесс на машине разработчика.

### Почему не QEMU в контейнере

Потому что `/dev/kvm` надо пробросить в этот контейнер. Docker Desktop не даёт его ни на macOS, ни на
Windows — ровно тех хостах, которым этот тир нужнее всего. Запуск нативно переворачивает задачу:

| хост | гость | ускоритель |
|---|---|---|
| macOS, Apple Silicon | aarch64 (`armsr/armv8`) | hvf |
| macOS, Intel | x86_64 | hvf |
| Linux | совпадает с хостом | kvm |
| Windows | совпадает с хостом | whpx |

На Apple Silicon это девять секунд до загрузки без вложенной виртуализации, без минимальной версии
macOS и без особого железа.

### Выбор ускорителя

Первый вопрос — **совпадает ли CPU гостя с CPU хоста**. Какой ускоритель есть у хоста, важно уже
потом. Никакой ускоритель не виртуализирует чужую архитектуру. x86-роутер на ARM-ноутбуке
транслируется инструкция за инструкцией, примерно на порядок медленнее. `arch: auto` (по умолчанию)
делает правильную вещь сам, а owlab громко предупреждает, чтобы не тормозить молча.

Всё остальное проверяется пробой и не выводится из ОС. Homebrew-овский `qemu-system-x86_64` на Apple
Silicon сообщает только `tcg`. Он собран без hvf, потому что hvf не может исполнять x86-гостя на
ARM-процессоре. `qemu-system-aarch64` из той же бутылки hvf умеет. Ни одно правило про macOS этого не
угадает.

На Linux «собран с kvm» не то же самое, что «разрешено им пользоваться». `/dev/kvm` принадлежит
`root:kvm`. Пользователь вне этой группы получает ошибку прав от QEMU сильно позже того момента, где
внятное сообщение бы помогло. owlab открывает устройство, чтобы выяснить это заранее.

owlab передаёт `-cpu host` только при родном ускорителе. Под трансляцией это была бы просьба к QEMU
эмулировать то, чем машина случайно оказалась. Это и медленнее, и менее воспроизводимо, чем названная
модель.

### Образы VM

owlab грузит апстримные combined-образы диска: ядро, загрузчик и rootfs в одном файле.

```
openwrt-25.12.5-armsr-armv8-generic-squashfs-combined-efi.img.gz
```

**squashfs вместо ext4.** squashfs — это то, на чём работает роутер: read-only `/rom` с пишущим
оверлеем сверху. Благодаря этому `firstboot`, `jffs2reset` и вся история сброса к заводским ведут себя
как на железе. ext4-образ — одна плоская пишущая файловая система, которая половину этого тихо делает
непроверяемым.

#### Подходят четыре таргета

Планка — апстрим публикует **combined**-образ:

- `x86_64`
- `i386_pentium4`
- `aarch64_generic` (armsr/armv8)
- `arm_cortex-a15_neon-vfpv4` (armsr/armv7)

malta публикует голое ядро и отдельный rootfs. mvebu — настоящая плата, которой нечем грузиться под
QEMU. Для любой из них owlab пришлось бы изобретать схему загрузки, которую апстрим никогда не
тестирует. «Грузится, но не так, как настоящий» — единственный исход, ради недопущения которого этот
тир и существует.

#### Прошивка для EFI-образов

armsr публикует только EFI-образы, так что aarch64 и armv7 нужна сборка edk2 на хосте. owlab ищет её
в таком порядке:

1. `OWLAB_FIRMWARE`, если переменная задана;
2. рядом с бинарём QEMU — это верно и для Homebrew, и для ручной сборки, и для пакета дистрибутива;
3. в обычных местах дистрибутивов, под обычными именами дистрибутивов (`AAVMF_CODE.fd`,
   `QEMU_EFI.fd`).

x86 по-прежнему публикует combined-образ с legacy-загрузкой, который SeaBIOS обрабатывает, ничего не
разыскивая.

#### Контрольные суммы без подписей

Образы сверяются с опубликованным `sha256sums`. Этот файл приходит с того же сервера по тому же
TLS-соединению, что и образ. Так что он ловит оборванную закачку или сломанное зеркало.
Скомпрометированный сервер загрузок он не ловит.

Апстрим публикует ещё `sha256sums.asc`. Его проверка требует релизного keyring, а это решение о
доверии выше того, что дев-инструмент вправе принимать за пользователя.

### Диски VM

Их два, и один из них существует из-за жёсткого ограничения.

| Диск | Что это |
|---|---|
| `disk.qcow2` | оверлей qcow2, чей backing-файл — кешированный образ; базу никто не пишет, так что одна закачка обслуживает каждый роутер и каждый проект на машине |
| `overlay.qcow2` | второй диск; `/overlay` переносится на него штатным extroot OpenWrt — тем же механизмом, которым настоящий роутер использует USB-флешку |

Второй диск необходим, удобство тут ни при чём. Оверлей в апстримном combined-образе зафиксирован на
этапе сборки (87 МБ на armsr). Он **не растёт изнутри работающей системы**. Файловая система создана
без resize inode, так что онлайновый `resize2fs` останавливается после первой группы блоков. Замерено:
раздел на 900 МБ дал 122 МБ.

У отдельного диска такой истории нет. Он стоит одной перезагрузки при первом провижининге и растёт
разреженно: диск на 2 ГБ занимает только то, что на него записано.

`disk: 0` это выключает и оставляет собственный оверлей образа.

### Сеть VM

Две сетевые карты, и порядок — это и есть замысел.

`board.d` в OpenWrt делает первый ethernet-порт LAN, а второй WAN:

- **LAN** получает статический 192.168.1.1. Там принимают соединения uhttpd и dropbear.
- **WAN** получает DHCP. Там firewall режет всё входящее.

Проброс портов хоста на WAN-сторону дал бы роутер, который поднят, недостижим ни для чего и обвинён в
этом QEMU.

LAN-сети SLIRP отдаётся собственная подсеть гостя:

```
-netdev user,id=lan,net=192.168.1.0/24,host=192.168.1.254,hostfwd=tcp::8090-192.168.1.1:80
```

`hostfwd` может достучаться только до адреса, который SLIRP считает своим. Адрес гостя фиксирует
`config_generate` раньше, чем owlab успевает сказать обратное.

WAN — обычная сеть SLIRP. Она даёт роутеру маршрут по умолчанию и работающий DNS, чтобы менеджер
пакетов доставал фиды. Это NAT, так что ничего из сети хоста не выставляется наружу.

Подключается `virtio-rng-pci`, потому что загрузка OpenWrt ждёт энтропии: urngd, хост-ключи dropbear,
оверлей. Headless-VM почти нечем наполнять пул ядра.

### Жизненный цикл VM

QEMU отвязывается через `-daemonize`, который заодно пишет pidfile.

На Windows такого флага нет. Там owlab запускает процесс с
`DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` и сам пишет pidfile. Обе половины этой пары нужны:

- без первой закрытие терминала доставляет `CTRL_CLOSE_EVENT` и уносит роутер с собой;
- без второй Ctrl-C во время `owlab up` прерывает роутер, а должен прерывать ожидание.

#### Проверка выхода через две секунды

Запуск вместо выполнения до конца стоит того единственного, что `-daemonize` даёт даром, — кода
возврата. QEMU, отвергнувший аргумент, выглядел ровно как успешная загрузка. Это всплывало через
минуту таймаутом ожидания ssh, который ничего не называл.

Поэтому owlab ждёт две секунды. QEMU, успевший к этому моменту завершиться, показывается вместе с тем,
что он написал в stderr.

#### Живость и энтропия зависят от ОС

Pidfile переживает процесс, который его написал, поэтому живость проверяется и не принимается на
веру: сигналом 0 на unix и `tasklist` на Windows, где сигналов нет.

Источник энтропии — второе, что различается. `rng-random` читает символьное устройство, а
`/dev/urandom` на Windows не существует, так что QEMU выходит до старта гостя. `rng-builtin` для
гостя тот же virtio-rng, но не требует файла на хосте. Windows достаётся `rng-builtin`.

#### Выключение и консоль

`owlab down` просит **гостя** выключиться по ssh и не убивает QEMU. Оверлей — настоящая файловая
система с настоящими грязными страницами. Выдёргивание вилки на каждом `down` рано или поздно стоило
бы кому-то установленных пакетов. Убийство — запасной путь для роутера, зависшего настолько, что не
отвечает.

Консоль пишется в файл (`-serial file:`), и это то, что показывает `owlab logs`. Это тот же поток, что
и лог контейнера, с первой строки ядра. Общение с роутером идёт по ssh, где у шелла есть настоящий
терминал.

### Провижининг

Диск и есть кеш. Провижининг выполняется один раз, на новом диске. Маркер, записанный в конце, делает
каждый следующий `owlab up` обычной загрузкой.

Порядок важен, и каждый шаг в нём оказался там по измеренной причине:

1. **extroot**, затем перезагрузка. Всё после этого пишет в файловую систему, которую он переносит.
2. **Пакеты**, затем пакеты не из фидов.
3. **Радио**: установка `kmod-mac80211-hwsim` и запись `/etc/modules.d/mac80211-hwsim` с запрошенным
   количеством.
4. **Перезагрузка.** Она нужна, это не косметика: см. ниже.
5. **Оверлей и фикстуры**, затем `wifi up`.

### Почему перезагрузка до оверлея

Всё, что выше, ставилось на систему, которая уже закончила загружаться. Изрядная часть OpenWrt читает
свои входы ровно один раз, при загрузке. Каждое из этого замерено на роутере, выглядевшем полностью
настроенным, и ни одно не сообщает ничего, что называло бы причину:

| Компонент | Что читает при загрузке | Без перезагрузки |
|---|---|---|
| **procd** | сервисы, включённые пакетом, `wpad` в их числе | никогда не замечает появившийся позже |
| **netifd** | `/lib/netifd/wireless/*` | `wifi-scripts`, поставленные позже, оставляют `wifi up` с ответом `Command failed: Not found` против netifd без загруженной поддержки wireless |
| **ubusd** | `/usr/share/acl.d/` | ACL от wpad — то, что вообще позволяет hostapd (работающему под непривилегированным пользователем `network`) опубликовать свой ubus-объект; без этого объекта скрипт настройки ждёт вечно, и радио остаются в `pending: true` |
| **kmodloader** | `/etc/modules.d/*` | радио hwsim появляются на свет только при загрузке |

Перезагрузка идёт **до** оверлея, потому что фикстурам нужно увидеть результат. `60-wifi.sh`
спрашивает, есть ли настоящие phy, и настраивает их, если есть. На одну перезагрузку раньше он не нашёл
бы ни одного и записал бы выдуманные радио, которые получает контейнер.

### Радио

Два phy `mac80211_hwsim` по умолчанию, и они настоящие:

```console
$ owlab exec real -- iwinfo
phy0-ap0  ESSID: "owlab"
          Mode: Master  Channel: 6 (2.437 GHz)  HT Mode: HT20
          Tx-Power: 20 dBm  Link Quality: 70/70
          Encryption: WPA-PSK (CCMP)
phy1-ap0  ESSID: "owlab"
          Mode: Master  Channel: 36 (5.180 GHz)  width: 80 MHz
          Tx-Power: 23 dBm  Link Quality: 70/70
```

Радио берутся из `/etc/modules.d/`, без `modprobe`. Они должны существовать раньше, чем netifd их
ищет, и так об этом говорит OpenWrt. Количество — параметр самого модуля. Поэтому два радио — это два
phy, то есть двухдиапазонный роутер с отдельным phy на каждый диапазон.

#### Диапазоны и каналы назначаются

Диапазоны и каналы назначаются, без автоопределения. `wifi config` ставит каждое радио hwsim на 6 ГГц
с каналом auto. Симулированный phy заявляет все диапазоны, а 6 ГГц самый высокий. При регуляторном
домене по умолчанию это даёт канал 0 без ширины, которую интерфейс мог бы назвать.

Поэтому owlab назначает их сам:

- первое радио получает 2.4 ГГц, канал 6;
- второе — 5 ГГц, канал 36;
- выставляется страна. При `00` регуляторный домен не разрешает почти ничего, а каналы 5 ГГц
  поднимаются выключенными.
