# Ранбук owlab

[English](runbook.md)

Процедуры для тех, кто разрабатывает пакет LuCI с owlab. Каждая — задача, команды и способ
убедиться, что вышло.

- **Проверка для любой машины — `owlab doctor`.** Он называет, что есть, чего нет и чем грозит
  каждое отсутствующее.
- **Каждая процедура заканчивается «Проверкой».** Не идите дальше, пока она не прошла.
- **Другие страницы:** что означает ключ — в [справочнике](reference_ru.md). Почему owlab так себя
  ведёт — во [внутренностях](internals_ru.md). Когда что-то сломалось — в
  [диагностике](troubleshooting_ru.md), она отсортирована по симптомам.

## Поставить owlab на эту машину

Нужны один бинарь на Go и один контейнерный движок. По платформам различаются только две вещи:
откуда берётся движок и, для `fidelity: vm`, откуда берётся QEMU.

| Платформа | Контейнерный движок | Ускорение VM (`fidelity: vm`) |
|---|---|---|
| [Linux](#linux) | Docker, Podman или что угодно ещё с Compose v2 | KVM, если вы в группе `kvm` |
| [WSL2](#wsl2) | Docker, поставленный в WSL, или Docker Desktop с WSL-интеграцией | KVM: WSL2 отдаёт `/dev/kvm` |
| [macOS](#macos) | Docker Desktop, OrbStack, Colima или Rancher Desktop | hvf |
| [Windows](#windows) | Docker Desktop с бэкендом WSL2 | whpx, после включения Платформы гипервизора Windows |

После установки выполните [проверку, общую для всех четырёх](#проверить-установку).

### Linux

1. Поставьте owlab и запустите проверку:

   ```console
   $ go install owfeed.org/owlab/cmd/owlab@latest
   $ owlab doctor
   ```

   Без тулчейна Go возьмите `owlab_<версия>_linux_<арх>.tar.gz` из
   [последнего релиза](https://github.com/owfeed/owlab/releases/latest) и положите бинарь в `PATH`.
2. Поставьте контейнерный движок: Docker, Podman или что угодно ещё с Compose v2.
3. Для `fidelity: vm` поставьте QEMU и вступите в группу `kvm`:

   ```console
   $ sudo apt install qemu-system-x86 qemu-system-arm     # или то же самое через dnf
   $ sudo usermod -aG kvm "$USER"                          # и перелогиниться
   ```

Про группу `kvm` забывают чаще всего. Без неё QEMU, собранный с KVM, всё равно скатывается в
трансляцию. Doctor говорит, что из двух получилось.

### WSL2

1. Откройте дистрибутив WSL. Ставьте и запускайте owlab **внутри** него. Из PowerShell по пути
   `\\wsl$` owlab не запускайте.
2. Выполните команды из раздела [Linux](#linux).
3. Возьмите Docker, поставленный в WSL, или Docker Desktop с включённой WSL-интеграцией.
4. Держите проект в файловой системе WSL: `~/src/luci-app-mine`. Путь вида `/mnt/c/Users/...` не
   годится.

Doctor предупреждает, когда рабочий каталог лежит под `/mnt`.

`fidelity: vm` здесь работает. WSL2 отдаёт `/dev/kvm`, и роутер грузится на настоящем ядре на
полной скорости.

<details>
<summary>Почему проекту нельзя лежать на диске Windows</summary>

Диск Windows виден через слой трансляции, который не пробрасывает inotify. Из-за этого
`owlab sync --watch` не сработает ни разу. Кроме того, каждое чтение файла достаточно медленное,
чтобы это было заметно на дереве размером с LuCI.

</details>

### macOS

```console
$ go install owfeed.org/owlab/cmd/owlab@latest
$ brew install qemu        # только для fidelity: vm
$ owlab doctor
```

Движок — Docker Desktop, OrbStack, Colima или Rancher Desktop.

На Apple Silicon архитектура роутера по умолчанию aarch64. VM-tier идёт через hvf — загрузка за
девять секунд. Попросить там `x86_64` можно, но он будет транслироваться, и doctor скажет об этом
до того, как ждать.

### Windows

owlab — обычная консольная программа и запускается из PowerShell. Из особой настройки под Windows
нужен только `PATH`.

#### Поставить owlab

1. Поставьте owlab, добавьте его в `PATH` на текущую сессию и запустите проверку:

   ```powershell
   go install owfeed.org/owlab/cmd/owlab@latest
   $env:PATH += ";$env:USERPROFILE\go\bin"        # на текущую сессию
   owlab doctor
   ```

2. Чтобы `PATH` сохранился между сессиями, добавьте каталог в «Параметры > Система > О системе >
   Дополнительные параметры системы > Переменные среды» или выполните:

   ```powershell
   [Environment]::SetEnvironmentVariable('PATH', "$env:PATH;$env:USERPROFILE\go\bin", 'User')
   ```

Без тулчейна Go распакуйте `owlab_<версия>_windows_<арх>.zip` из
[последнего релиза](https://github.com/owfeed/owlab/releases/latest) в постоянное место. Так же
добавьте этот каталог в `PATH`. Публикуются и `amd64`, и `arm64`.

#### Контейнерный движок

Нужен Docker Desktop с бэкендом WSL2. Контейнеры здесь линуксовые:

- Не переключайте Docker Desktop в Windows containers.
- `docker version` обязан показывать линуксовый сервер.

#### QEMU для `fidelity: vm`

1. Поставьте QEMU:

   ```powershell
   winget install SoftwareFreedomConservancy.QEMU
   ```

   В `PATH` после этого ничего добавлять не нужно. Установщик туда QEMU не кладёт. owlab сам
   смотрит в `C:\Program Files\qemu` и в каталоги scoop и chocolatey. `owlab doctor` печатает,
   какой бинарь он выбрал. Если QEMU у вас вообще в другом месте, задайте
   `OWLAB_QEMU=C:\путь\к\qemu-system-x86_64.exe`.
2. Включите **Платформу гипервизора Windows** (Windows Hypervisor Platform), она выключена по
   умолчанию. В PowerShell от администратора выполните:

   ```powershell
   dism.exe /Online /Enable-Feature /All /FeatureName:HypervisorPlatform
   ```

3. Перезагрузитесь.

Без Платформы гипервизора у QEMU нет `whpx`, и всё уходит в трансляцию: минуты на загрузку вместо
секунд. Doctor говорит, что из двух у вас получилось, так что засекать время не придётся.

Если VM не грузится вовсе или виснет на середине с включённым ускорением, попробуйте
`$env:OWLAB_ACCEL="tcg"`. Трансляция медленная, но работает всегда.

<details>
<summary>Почему ускорение не работает на некоторых машинах</summary>

WHPX лежит поверх Hyper-V, и есть машины, на которых он не работает. Понять, с чем из двух имеешь
дело, — первое, что стоит установить.

</details>

#### Необязательные компоненты Windows, которые проверяет doctor

Обе вещи — необязательные компоненты Windows, их нет по умолчанию. Поэтому doctor проверяет их
именно здесь:

- **Клиент OpenSSH**, в «Параметры > Система > Дополнительные компоненты». До роутеров
  `fidelity: vm` owlab добирается по ssh. До контейнерных — нет, так что проекту без VM он не
  нужен.
- **POSIX-шелл**, если у проекта задан `project.build`. Это командная строка шелла, и выполняет её
  `sh`. Git for Windows такой приносит. Ничем другим он не подменяется: отдать POSIX-строку в
  `cmd.exe` значит тихо выполнить не то.

#### Переводы строк

Скрипты пакета исполняет busybox. Он читает шебанг с CRLF как имя команды, оканчивающееся на `\r`,
и сообщает `bad interpreter: /bin/sh^M`.

1. Добавьте в `.gitattributes` проекта:

   ```
   * text=auto eol=lf
   ```

2. Выполните `git add --renormalize .`.

Doctor ищет CRLF и падает на нём, потому что ничто дальше по цепочке причину не назовёт.

## Начать работу над пакетом

Если `owlab.yaml` ещё нет, вот минимальный рабочий:

```yaml
version: 1
routers:
  - id: owrt2512
    release: "25.12.5"
```

Затем поднимите роутер и откройте его:

```console
$ cd ~/src/luci-app-mine
$ owlab up
$ owlab open owrt2512
```

Проверка: LuCI отвечает, пункт меню вашего пакета на месте.

```console
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/
200
```

## Цикл правок

```console
$ owlab sync --watch
```

Оставьте работать. Каждое сохранение копирует дерево на роутер и сбрасывает кеши LuCI.
Перезагрузите страницу.

Проверка: правьте файл, видимый в браузере, дождитесь строки ниже и обновите страницу.

```
  owrt2512   42 files, 846 KB
```

Если пакет генерирует ассеты, например `cascade.css` темы или скомпилированные переводы, объявите
сборку. Иначе sync скопирует дерево без ровно того файла, который LuCI и запрашивает:

```yaml
project:
  build: ./build-css.sh htdocs/luci-static/mytheme/cascade.css
```

## Проверить на другом релизе

Добавьте роутер и поднимите. Больше ничего менять не нужно.

1. Добавьте роутер в `owlab.yaml`:

   ```yaml
   routers:
     - id: owrt2410
       release: "24.10.8"
   ```

2. Поднимите его и синхронизируйте:

   ```console
   $ owlab up owrt2410
   $ owlab sync owrt2410
   ```

Проверка: `owlab status` показывает `running`. Обратите внимание на колонку `PKGMGR`: на 24.10 это
opkg, на 25.12 apk. Эта разница и есть главная причина держать вторую коробку.

## Узнать, не устарели ли пины

```console
$ owlab releases
ROUTER      DISTRO    PINNED    NEWEST
owrt2512    openwrt   25.12.4   25.12.5   1 release behind
owrt2410    openwrt   24.10.8   24.10.8   up to date
```

Чтобы сдвинуть пин:

1. Поправьте `release:` в `owlab.yaml`.
2. Пересоберите роутер:

   ```console
   $ owlab up --rebuild owrt2512
   ```

Проверка: `owlab releases` говорит up to date, а эта команда показывает запиненный релиз:

```console
$ owlab exec owrt2512 -- 'ubus call system board | grep version'
```

Не пиньте `snapshot`. Snapshot-образы и snapshot-фиды пересобираются ежедневно и независимо,
поэтому установки начинают падать в течение суток.

### Проверить копии пина

`images/owlab.yaml` — пин, который правит человек. Тот же номер релиза скопирован ещё в
`images/Dockerfile`: он поднимает роутер, не читая этот конфиг. В воркфлоу копий нет: `ci.yml`
читает релизы из `images/owlab.yaml` во время прогона.

```console
$ sh tools/pins.sh check
images/owlab.yaml pins: 24.10.6 24.10.8 25.12.1 25.12.5
no workflow names a release; every release literal in the pin files is one images/owlab.yaml pins
```

`ci.yml` запускает эту проверку на каждый push. Она падает в двух случаях:

| Падает, когда | Чем это важно |
|---|---|
| **Воркфлоу называет любой релиз**, даже запиненный | `pins.yml` пушит с `GITHUB_TOKEN`. GitHub отклоняет от него push, меняющий `.github/workflows/`, поэтому литерал там — пин, который ничто автоматическое не сдвинет. Берите релиз из джобы `routers` в `ci.yml`. |
| **`images/Dockerfile` называет релиз, которого нет среди пинов `images/owlab.yaml`** | Больше это не ловит ничто. Старый релиз всё ещё собирается, поэтому забытая копия остаётся зелёной, а CI тестирует релиз, на котором никто не работает. |

Сдвинуть все копии одного релиза сразу:

```console
$ sh tools/pins.sh bump 25.12.4 25.12.5
```

Комментарии, `examples/`, README и `docs/` сохраняют тот релиз, который в них написан. Обе команды
их не трогают.

<details>
<summary>Почему номера релизов в тексте не сдвигаются</summary>

Номер релиза в тексте — иллюстрация. Пример вывода в начале этого раздела намеренно показывает пин,
отставший на один релиз.

</details>

### Джоба, которая предлагает сдвиг

`pins.yml` запускается ежедневно и задаёт `owlab releases --json` тот же вопрос. Когда ответ не
«up to date», она открывает пулл-реквест:

1. Переписывает пины.
2. Прогоняет по результату `tools/pins.sh check` и `owlab context --list`.
3. На этом останавливается. В `main` она не пишет никогда.

То, что новый релиз всё ещё собирает роутер, доказывает прогон CI на этом пулл-реквесте. Бóльшая
цифра в листинге каталога этого не доказывает.

**Ей нужна одна настройка репозитория.** Включите **Settings → Actions → General → Allow GitHub
Actions to create and approve pull requests**. Без неё джоба пушит ветку и останавливается на:

```
pull request create failed: GraphQL: GitHub Actions is not permitted to create or approve pull requests (createPullRequest)
```

Включить настройку — это весь фикс. Следующий прогон заменит оставленную ветку и откроет
пулл-реквест.

**Смотрите запущенные джобой проверки, задержанную не ждите.** У пулл-реквеста, открытого через
`GITHUB_TOKEN`, прогон `pull_request` встаёт в `action_required`. GitHub делает так с каждым таким
пулл-реквестом, поэтому `pins.yml` сам запускает `ci.yml` на ветке. Сливайте, когда этот прогон
зелёный.

## Поставить свой пакет по URL

1. Добавьте оба URL в `owlab.yaml`:

   ```yaml
   defaults:
     extra_packages:
       - name: luci-app-mine
         apk: https://github.com/you/mine/releases/download/v1.0/luci-app-mine-1.0-r1.apk
         ipk: https://github.com/you/mine/releases/download/v1.0/luci-app-mine_1.0-r1_all.ipk
   ```

2. Пересоберите:

   ```console
   $ owlab up --rebuild
   ```

Проверка: сборка печатает `owlab: installing luci-app-mine-1.0-r1.apk`.

- **Указывайте оба URL**, потому что apk и opkg не делят схему именования.
- **Пиньте точный релиз**, ссылку на `latest` не используйте: подписи здесь не проверяются.

Если пакет поставить не удалось, сборка продолжается и этот роутер стартует без него. Один плохой
файл не отменяет остальные роутеры. Сбой виден в трёх местах:

- `owlab up` называет недостающее после своей таблицы и завершается с ненулевым кодом.
- `owlab test` роняет этот роутер на шаге `extra_packages`.
- Список остаётся на роутере в `/etc/owlab/extras-failed`.

## Собрать настоящий .apk или .ipk

Делайте это перед каждым релизом. Настоящая сборка минифицирует JS и CSS, sync этого не делает. На
этой разнице ломались пакеты, прекрасно работавшие на дев-боксе.

```console
$ owlab build
$ owlab install owrt2512 dist/noarch/luci-app-mine-1.0-r1.apk
```

Проверка: файл лежит в `dist/`, и роутер отдаёт то же самое, что отдавал после sync.

Если менеджер пакетов отказался ставить файл, `owlab install` выходит с кодом 1 и называет роутер.
Файл, чьи зависимости уже есть на роутере, ставится без обращения к фидам. Иначе owlab обновляет
фиды и ставит ещё раз.

На Apple Silicon сборка идёт под эмуляцией, потому что все теги `openwrt/sdk` — это `linux/amd64`.
Будет медленно. owlab предупреждает до старта.

## Проверять пакет в CI

В репозитории пакета, без всякого `owlab.yaml`:

```yaml
- uses: owfeed/owlab/setup@v0.8.0
- run: owlab build --release 25.12.5 --out dist   # .apk для 25.12
- run: owlab build --release 24.10.8 --out dist   # .ipk для 24.10
- uses: owfeed/owlab/action@v0.8.0
  with:
    releases: "25.12.5 24.10.8"
    install: dist/*/luci-app-mine-*
    assert: |
      package luci-app-mine
      http 200 /cgi-bin/luci/admin/services/mine
```

Проверка: в summary джоба по строке на роутер. Сломанный пакет красит одну из них в красный и
называет упавшую проверку.

Перед пушем запустите то же самое локально. Это та же команда, и ей не нужно ничего, кроме Docker:

```console
$ owlab test --release 25.12.5 --install 'dist/*/luci-app-mine-*.apk' \
    --assert 'http 200 /cgi-bin/luci/admin/services/mine'
```

Суффикс `.apk` совпадает только со сборкой apk, которую ставят 25.12 и новее. Роутер 24.10 читает
`.ipk` и остался бы без пакета. Чтобы проверить обе линии релизов, уберите суффикс, как в шаге экшена
выше.

Если проверка упала и хочется посмотреть на страницу глазами, добавьте `--keep`: он оставляет
роутеры поднятыми. В CI его не ставьте. Снос не даёт упавшему прогону держать порты, нужные
следующему.

Готовый workflow для копирования — в
[examples/workflow/package-ci.yml](../examples/workflow/package-ci.yml). Все флаги — в
[справочнике](reference_ru.md#owlab-test).

## Работать с модулями ядра

Контейнер модули ядра не грузит. Нужен VM-роутер:

```yaml
routers:
  - id: real
    fidelity: vm
    release: "25.12.5"
    packages: ["+kmod-nft-tproxy"]
```

```console
$ owlab up real
$ owlab exec real -- 'uname -r; lsmod | grep nft_tproxy'
6.12.94
nft_tproxy    12288  0
```

Проверка: модуль в `lsmod`. В контейнере он ставится файлом и не грузится никогда.

- **Первый старт:** около полутора минут. Это скачивание, extroot, пакеты и две перезагрузки.
- **Дальше:** двадцать секунд.
- **Диск** переживает `owlab down`. Сбрасывает его только `--rebuild`.

## Работать с WiFi

VM-роутер получает два радио `mac80211_hwsim`, и они настоящие.

```console
$ owlab exec real -- iwinfo
phy0-ap0  ESSID: "owlab"  Channel: 6 (2.437 GHz)  HT20  Tx-Power: 20 dBm
phy1-ap0  ESSID: "owlab"  Channel: 36 (5.180 GHz)         Tx-Power: 23 dBm
```

Проверка: `ubus call network.wireless status` показывает `"up": true` у обоих.

В контейнере вместо этого `fixtures: [wifi]` засевает конфиг:

- **Отрисуются:** меню, список радио, SSID, режимы и вся форма редактирования.
- **Останутся пустыми:** сигнал, результаты сканирования и таблица клиентов. Это приходит от
  настоящего радио.

## Достучаться до сервиса, который не HTTP и не ssh

owlab пробрасывает только HTTP и ssh. Остальное — форвардом через ssh:

```console
$ IP=$(owlab exec pk2512 -- 'uci get network.lan.ipaddr')
$ ssh -f -N -p 2295 -L 1080:$IP:2080 root@localhost
$ curl -x socks5h://127.0.0.1:1080 https://ifconfig.me
```

Проверка: адрес отличается от прямого `curl https://ifconfig.me`.

## Роутер перестал отвечать

1. Посмотрите статус и лог:

   ```console
   $ owlab status
   $ owlab logs owrt2512 --tail 50
   ```

2. Проверьте, по убыванию вероятности:

   ```console
   $ owlab exec owrt2512 -- 'service uhttpd status; netstat -lnt | grep :80'
   $ owlab exec owrt2512 -- 'nft list chain inet fw4 input | head'
   $ owlab exec owrt2512 -- 'ip route; ping -c1 -W3 8.8.8.8'
   ```

| Симптом | Причина |
|---|---|
| TCP-рукопожатие завершается, и соединение тут же сбрасывается, а uhttpd жив и слушает | [flow offloading](troubleshooting_ru.md#роутер-сбрасывает-каждое-соединение) |
| LuCI отдаётся, но любое исходящее соединение висит | [mwan3](troubleshooting_ru.md#luci-отвечает-но-исходящее-не-работает) |

## Начать с нуля

```console
$ owlab up --rebuild          # выбросить роутеры и собрать заново
$ owlab down --purge          # и снести образы с дисками VM
```

`--rebuild` — это сброс к заводским. Всё, поставленное через `owlab install`, любая правка uci
руками и весь диск VM исчезают.

## Переехать на другую машину

Всё, что нужно owlab, — это `owlab.yaml` и ваше дерево исходников. Состояния за пределами каталога
проекта и одного кеша образов нет.

На новой машине выполните:

```console
$ owlab doctor
```

Проверка: ни одной строки `FAIL`. Предупреждения — это ограничения той машины, ошибками они не
считаются. Читайте их: там написано, что именно там не заработает.

## Указать конфиг в другом месте

```console
$ owlab --config ../other-project/owlab.yaml up
$ owlab --config ../other-project status        # каталог тоже подойдёт
$ export OWLAB_CONFIG=~/src/other-project
```

`--config` работает и до имени команды, и после. Без него owlab ищет в текущем каталоге и выше.
