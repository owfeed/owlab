# Релизы

[English](releasing.md)

Как выпустить версию owlab и что происходит после пуша тега. Для мейнтейнера, который может пушить
теги в репозиторий.

- **Тег — единственный вход.** Из него берутся версия в бинаре, имена архивов, заголовок релиза и его
  тело.
- **Changelog — условие релиза.** Релиз падает, если в `CHANGELOG.md` нет секции под эту версию.
- **Образы роутеров** публикует отдельный воркфлоу, `images.yml`. Они никогда не удаляются.

## Выпуск версии

1. В `CHANGELOG.md` сдвиньте заголовок `## [Unreleased]` до версии с датой.
2. Внизу `CHANGELOG.md` добавьте ссылку сравнения.
3. Переведите все ссылки на версию из таблицы ниже на тег, который вот-вот появится.
4. Создайте тег и запушьте его:

   ```console
   $ git tag -a v0.2.0 -m 'owlab 0.2.0'
   $ git push origin v0.2.0
   ```

Это вся процедура.

### Что двигается при релизе

| Ссылка | Где |
|---|---|
| `owlab/action@vX.Y.Z` и `owlab/setup@vX.Y.Z`, включая короткие формы в тексте (`setup@…`, `action@…`) | `SECURITY.md`, оба README, `docs/` и `examples/workflow/` |
| Версия в тексте рядом с ними, например «ставит vX.Y.Z» | `SECURITY.md` и `docs/` |
| Пример `gh release download`, имя архива в нём и в следующей за ним строке `gh attestation verify` | `SECURITY.md` |

Двигайте их *до* тега. Тогда в теге лежат README и пример, указывающие на него самого.

<details>
<summary>Почему теги точные, без плавающего <code>v1</code></summary>

Экшен решает, сломан ли чей-то пакет. Репозиторий, запинивший `owlab/action@vX.Y.Z`, должен получить
ровно то поведение проверок, которое с этим тегом ревьюили. Поведение не должно меняться без единого
коммита в его репозитории.

</details>

### Проверить, что получилось

Последний шаг релизного воркфлоу скачивает `releases/latest/download/SHA256SUMS` и сверяет с тем, что
собрал этот прогон. Если шаг прошёл, `releases/latest` отдаёт `SHA256SUMS` этого прогона.

404 здесь означает, что все скачивания провалились бы. Это последний момент, когда это красная сборка,
а не баг-репорт.

## Что делает тег

`release.yml` выполняет шаги:

1. Собирает шесть архивов: linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, windows/amd64 и
   windows/arm64. В каждом бинарь, README, changelog, лицензия и `docs/`.
2. Пишет `SHA256SUMS`.
3. Публикует релиз **черновиком**.
4. Переводит черновик в опубликованные.
5. Скачивает `releases/latest/download/SHA256SUMS` и сверяет с тем, что собрал этот прогон.

Каждый архив получает attestation до загрузки.

<details>
<summary>Почему релиз начинается с черновика</summary>

`releases/latest` сдвигается в момент публикации. Экшн загрузки сначала создаёт релиз и только потом
заливает ассеты. Поэтому у релиза, опубликованного сразу, есть окно, в котором `latest` указывает на
пустоту.

Черновик не становится `latest`, поэтому переключение происходит один раз, когда всё уже на месте.

</details>

### Как проверяется attestation

- `owlab/setup` проверяет attestation с `--signer-workflow`: одного `--repo` недостаточно.
- Проверка идёт до того, как бинарь будет запущен или попадёт в `PATH`.
- Непроверенный бинарь `owlab/setup` ставить отказывается.
- `SHA256SUMS` тоже публикуется, но проверку не заменяет. Его отдаёт тот же хост из того же релиза, так
  что кто может подменить одно, подменит и другое.

### Почему один сторонний экшн запинен по коммиту

`softprops/action-gh-release` запинен по коммиту. Тег `v3` для этого не используется. Это единственный сторонний экшн в
репозитории, и он работает в единственной джобе, которая может писать в релиз. Тот, кто может сдвинуть
этот тег, может публиковать ассеты под нашим именем.

## Номера версий

owlab следует semver, где поверхностью совместимости служит `owlab.yaml`.

- Конфиг `version: 1`, работающий сегодня, продолжит работать на минорных и патч-релизах.
- Изменение, которое его сломает, ждёт мажорного релиза.

Бинарь отвечает тремя способами, в порядке предпочтения:

1. Тем, что застемпила релизная сборка через `-ldflags -X main.version=…`.
2. Тем, что записала модульная система, — так `go install …@v0.2.0` знает свою
   версию.
3. `dev` — для обычного `go build` из чекаута.

Коммит и дата сборки приходят либо из стемпа, либо из VCS-информации, которую вшивает тулчейн Go.
Поэтому `owlab version` говорит правду в любом случае.

Дата сборки — дата коммита, не стенные часы. Пересборка того же тега должна давать тот же файл.

<details>
<summary>Почему версия здесь важнее, чем в большинстве инструментов</summary>

owlab несёт контекст сборки образов внутри бинаря. Поэтому «какой owlab собрал этот роутер» — реальный
вопрос.

</details>

## Образы роутеров

`images.yml` публикует в `ghcr.io/owfeed/owlab-rootfs`. Запускается еженедельно, на пушах, задевающих
входы образов, и после релиза.

Один тег — один таргет: дистрибутив, точный релиз, архитектура.

<details>
<summary>Почему один тег на таргет и нет manifest list</summary>

В OCI image index нет поля под «версию дистрибутива», а у большинства имён архитектур OpenWrt нет
валидного GOARCH-соответствия. Manifest list такую матрицу не выражает, и апстрим тоже не пытается.

</details>

### Слежение за апстримом

`images/owlab.yaml` пинит один релиз на ветку.

- **Пин** получает разработчик, собирающий локально.
- **Пин служит и полом.** Публикуется `keep` последних точечных релизов тех же веток, вычисленных на
  сервере загрузок во время сборки.
- **`keep`** по умолчанию 2. Это вход и для ручного запуска, и для вызова из релиза.

Так апстрим, тегнувший 25.12.5, кладёт образ на GHCR в ближайший понедельник без того, чтобы кто-то
правил номер версии. 25.12.4 остаётся доступным для тех, кто ещё не переехал.

Посмотреть текущее положение дел:

```console
$ cd images && owlab releases
```

#### Сдвинуть пин

Сдвинуть пин одной правкой нельзя. Тот же номер релиза скопирован в `images/Dockerfile`, а `ci.yml`
роняет копию, которая называет релиз, отсутствующий среди пинов `images/owlab.yaml`.

- Запустите `sh tools/pins.sh bump <старый> <новый>`. Он двигает все копии сразу.
- Или примите пулл-реквест от `pins.yml`: он предлагает этот сдвиг ежедневно.

Оба описаны в [ранбуке](runbook_ru.md#проверить-копии-пина).

Не вписывайте номер релиза в воркфлоу: `tools/pins.sh check` на нём падает. В воркфлоу номеров
релизов нет. `ci.yml` читает релизы для e2e из `images/owlab.yaml` во время прогона.

<details>
<summary>Почему воркфлоу читают пин во время прогона</summary>

`pins.yml` пушит с `GITHUB_TOKEN`, а GitHub отклоняет такой push, если он меняет файл в
`.github/workflows/`.

</details>

#### Что проверяет резолвер

Резолвер проверяет две вещи, о которых листинг не говорит:

- **У релиза есть артефакты для таргета.** Точечный релиз появляется в листинге, когда его тегнули.
  Образы конкретного таргета появляются, когда закончилась его сборка. Поверив листингу на слово,
  получаем джобу, которая падает на 404 через двадцать минут.
- **Запиненный релиз собирается всегда,** даже если он выпал из окна. Кто-то пинит его в собственном
  `owlab.yaml`, и еженедельная пересборка держит этот образ в тонусе со своим фидом.

Если сервер загрузок прочитать не удалось, матрица откатывается на пины. Джоба публикации, упавшая
из-за таймаута листинга, была бы хуже той, что опубликовала то, что уже написано в конфиге.

### Неизменяемые теги

Релиз добавляет второй тег рядом с плавающим:

```
ghcr.io/owfeed/owlab-rootfs:openwrt-25.12.5-x86_64          # двигается
ghcr.io/owfeed/owlab-rootfs:openwrt-25.12.5-x86_64-v0.2.0   # нет
```

- **Плавающий тег** пересобирается еженедельно и подхватывает изменения фида внутри того же
  запиненного релиза. Разрабатывайте против него, но не пиньте его.
- **Версионный тег** не меняется. Указывайте на него `image:`, когда нужны те же байты дважды.

## Ничего никогда не удаляется

Старые образы остаются на GHCR. Резолвер перестаёт **собирать** старые релизы, но не удаляет их.

Чей-то `owlab.yaml` на них ссылается, а тег, переставший резолвиться, — это сломанная сборка у
постороннего человека.
